# Passport 桥接协议

设备与它的配套桥接服务之间如何通信。设备是一个**薄终端**:桥接服务拥有会话、知道桌面在做什么,
并且只在需要人来回答时才向设备提问。

本文就是那份契约。设备侧已经实现,并且对着一个替身服务器
([`tools/mock_bridge.py`](../../../tools/mock_bridge.py))验证过;桥接服务本身是下一件事,而它背后
的桌面会话集成不在本文设计范围内。

## 1. 传输

**局域网内的明文 HTTP,不是 TLS。** 桥接服务是与设备同一网络上的配套进程,而且文档里不携带任何
凭据。跳过握手可以让**最大连续空闲块保持在 112 KiB 而不是 68 KiB**——这块板子的显示与音频通路
需要它。

后果要说出来而不是藏起来:**网络上任何东西都能提供状态文档或读取回答。** 不要在你无法控制的网络上
运行它。配置里已经预留了 `bridge_token`,供它在离开可信局域网之前加上认证。

`bridge_url` 是基地址,例如 `http://192.168.2.183:8080`。当工作模式可达且 station 已关联时,设备
每五秒轮询一次 `<bridge_url>/work-status`。

## 2. `GET /work-status`

返回一个 JSON 对象。**每个字段都是可选的**,设备读不到的字段会变成默认值而不是失败——因为一个
新增了字段的桥接服务不该把屏幕清空。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `task` | 字符串 | 会话正在做什么。显示在工作屏上。 |
| `progress` | 数字 0–100 | 完成比例。**缺失表示未知**,显示为 `--` 而不是空进度条;超出范围的值会被钳制。 |
| `state` | 字符串 | `running`、`waiting`、`done` 或 `failed`。其他值读作 idle。 |
| `question` | 字符串 | 给设备主人的问题。存在即表示设备可以作答。 |
| `option0` … `option3` | 字符串 | 选项。**是可编号字段而不是数组**:设备端的读取器是几百字节而不是解析器,而编号字段不需要分隔符转义,所以一个含逗号或引号的选项不可能破坏列表。 |
| `selected` | 数字 0–3 | 初始高亮哪一个。超出列表时忽略。 |

设备施加的规则(全部在宿主测试过、并在硬件上观察到):

- **选项列表在第一个空缺处结束。** `option0`、`option1` 之后没有内容即两个选项;孤立的 `option3`
  不算一个选项。
- **没有问题的选项不可选择。**
- **既没有 `task` 也没有 `question` 的文档会被拒绝**,设备继续显示上一份状态而不是清空。
- **配网屏打开时到达的文档不会接管屏幕。** 正在配网的人不该被后台更新顶出去。从主页则会接管。

示例:

```json
{"task":"deploy","state":"waiting","question":"Which branch?",
 "option0":"main","option1":"develop","option2":"release","selected":0}
```

## 3. `POST /answer`

当主人用按键确认选择时发出。

```json
{"answer":"develop"}
```

`answer` 是所选选项的**文本**,不是它的下标:文本才是人真正选中的东西,而且它在选项列表发生变化时
依然成立。桥接服务返回 `200` 与一个 JSON 体;设备记录状态码并在控制台里保留结果。非 200 意味着
回答没有送达,而设备会如实说明,而不是假装已送达。

**一个问题只接受一个答案。** 在新的文档到达之前,设备会拒绝针对同一个问题的第二次确认,所以连按
两次不会回答两遍。

## 4. 设备不做什么

- **不流式推送。** 整个机制就是每五秒轮询一次;变化比这更快的会话不是它要解决的场景。
- **还不会朗读或提示音。** 文档里没有"播报"指令,工作模式的音频通路也还没接。这是桥接服务存在之后
  的下一件事。
- **不做认证。** 见第 1 节。
