## 2026-10-15 —— 第 41 次会话：设备现在会"看得见地等",以及一个"长度"冒充回复

主人的报告既准确又正确:**"the bridge was still transcribing after six attempts"**——那是设备自己的放弃
消息——并指示:**加一个思考状态,然后等结果**。

### 三个互不相让的超时

原来的等待是"六次、每次间隔 400 毫秒":大约三秒。识别请求是一次**经过服务商的网络往返**,几秒钟是正常的,
而设备**在还在工作的中继上放弃了**。可是把等待拉长,又暴露了问题的另一半:**单次请求超时是 8 秒**,于是
一个**把请求挂住**(这是行为良好的做法——而不是回一句"还没好"让设备反复轮询)的中继,**会在即将回答之前
被设备自己的客户端掐断**。在真机上用"故意慢 8 秒"的中继测出来:

```text
bridge: transcription delayed by 8.0 s for testing
bridge: GET /voice/transcript -> 'which branch should I deploy'      (正确回答了)
device: last="transcript fetch returned HTTP -1"                     (在等待它的时候超时了)
```

现在三个数字互相让步,而且写在能互相对照的地方:

| | 值 | 为什么 |
| --- | --- | --- |
| 单次请求 | 15 秒 | 中继最多可以把一个请求挂多久 |
| 两次之间 | 0.5 秒 | 中继说"还没好"之后再问一次的间隔 |
| 总计 | 30 秒 | 超过就失败,并报出它等了多少秒 |

而中继把答案最多挂 **12 秒**,**刻意短于设备的单次请求超时**,于是一个"只是慢"的服务商会在**设备已经开着
的那个请求里**被回答。用同一个"慢 8 秒"的中继验证:这一回合完成了,转写到了,模型也回答了。

而且这个等待**现在是看得见的**——这正是主人要的:从音频送达那一刻到转写回来,屏幕上有一行"正在转写…",
宠物是 `THINKING` 表情。**没人看得见的等待,和死机无法区分**;而原来的代码**什么都不显示**——音频已经送达
了,日志这么写着,面板却一直停在上一句话上。

### 一个"长度"冒充回复

测这个修复时,翻出一个**独立的、早就存在的**缺陷,值得一字不差地记下来:

```text
屏幕: 你好！(Nǐ hǎo!)                  模型的回答,正确,显示在面板上
中继: GET /speak raw='text=%14'         单个字节,值是二十
```

二十正好是那句回答的**字节长度**。**朗读模块拿到的不是字符串,而是一个数字**,它照样拼出了一个请求,于是
设备请服务商去合成一个控制字符。它是**间歇性**的:下一条同样的命令**完整地把整句话送了出去**,percent
编码一切正常。固定缓冲里间歇出现的错值,正是"**有东西写过了相邻分配的边界**"的特征;那个回复缓冲正是
一起分配的两个之一,而第一步就是**别再把它交给 `malloc` 留下的任何东西**:

- 两个对话缓冲在分配时清零,所以没写过的回复是**空的**,而不是垃圾;
- 朗读模块**拒绝**首字节是控制字符的回复,把那个字节和长度记进日志,而不是把废话发给服务商。

**根因尚未确定,记为未解决。** 它是靠**检查线上字节**而不是相信任何一端发现的——和上一次会话里把日志
编码问题变成"非事件"的,是同一种纪律。

## 2026-10-15 —— 第 40 次会话：带上真密钥的中继,以及两个方向都被验证

主人给了一个硅基流动的密钥,所以替身答案可以换成真的了。服务商自己的文档还纠正了我的两个假设——这
正是"先读文档再猜 API"的价值:

- **音色名必须带上模型**:`FunAudioLLM/CosyVoice2-0.5B:claire`。只写 `anna` 会被拒绝:
  `{"code":20047,"message":"Invalid voice."}`——错误很明确,也正是第一次尝试失败的原因。八个预置音色是
  alex、benjamin、charles、david、anna、bella、claire、diana。
- **`sample_rate` 是请求参数**,所以 `response_format: pcm` 配 `sample_rate: 16000` **返回的正是设备要播的
  东西**。整条链路**不需要解码,也不需要重采样**——而这正是当初选 PCM 的全部理由。

### 两个方向,用真模型验证

中继现在有 `--selftest`:不需要设备、也不需要人,把两个方向来回跑一遍——让语音合成说一句话,再把返回的
音频**当作设备录下来的东西**喂回识别。

```text
selftest: 让服务商朗读 '你好,这是随身宠物在测试语音通路。'
  合成返回 107438 字节 16 kHz PCM(3.4 秒)
selftest: 把这段音频当作设备说过的话喂回去
  识别听到:'你好,这是随身宠物在测试语音通路。'
  听到的 17 个不同字符,17 个都出现在原句里
```

两个模型来回一趟,**逐字符**把原句还了回来——这超出了这个测试本来的期待。凭据、两种请求形态、采样率
处理因此都被走过了;而且**这是没有人在场时唯一能测"麦克风那一半"的办法**。

### 设备真的发出了声音

```text
voice speak hello there        -> 中继收到,设备播放了 14678 个采样
voice speak(上一句回答)         -> DeepSeek 的中文回答,播放 37079 个采样(16 kHz 下 2.3 秒)
```

第二个才是关键:中文回答来自模型,作为 URL 编码的查询送到中继,被硅基流动合成,然后**由设备播放出来**。
线上的字节是**查过**的,不是假设的——因为日志让它看起来是坏的:

```text
raw = text=%E4%BD%A0%E5%A5%BD%EF%BC%8C%E5%BE%88%E9%AB%98%E5%85%B4%E4%B8%BA%E4%BD%A0%E6%9C%8D%E5%8A%A1%E3%80%82
      = 那句回答,percent-encoded UTF-8,完全正确
```

**乱码在日志文件里,不在线上。** 中继是用**GBK 控制台重定向**启动的,于是内存里正确的 UTF-8 从日志里出来
变成了替换字符,**而设备有一瞬间被当成了犯错的一方**。中继现在会把自己的输出流强制设为 UTF-8,不管控制台
代码页是什么——因为**一份连作者自己都读不回来的日志,恰恰会制造这种错误结论**。

### 发现一个真实限制,但它不在语音通路上

在**串口控制台**上敲 `voice speak <中文>` 会**丢掉参数**:设备把字符正确回显出来,然后朗读了模型的上一句
回答,就像参数根本不存在一样。**往这个控制台里敲中文是不工作的**,这也意味着**中文 Wi-Fi SSID 没法在那里
输入**——Web 控制台能处理,而设备通常就是这么配的,但串口控制台**不应该悄悄做错事**。这条记为 CLI 的缺陷,
不在这里修,因为**它不在语音通路上**:转写从 HTTP 响应体里来,回答从 JSON 里来,两者都在上面被证明过了。

## 2026-10-15 —— 第 39 次会话：中继存在了,而它的每个端点都逐个验证过

主人问该用哪些语音服务、在哪儿找,并让我去找。两件都做了,然后是系统里**还只是一份文档**的那一半：
`tools/passport_bridge.py`。

### 推荐

两个方向都用**硅基流动**:一个密钥、一种 OpenAI 兼容形态同时覆盖语音识别与语音合成,而
`/v1/audio/speech` 能直接返回原始 PCM——**这意味着整条链路上没有任何音频解码器**,这也正是设备当初
就发 PCM 的理由。中文质量优先时次选**阿里云百炼**,代价是两种不同的 API 形态,而中继把这种不对称做成
了一个 provider 模式。理由与链接放在
[`voice-backends.zh_CN.md`](voice-backends.zh_CN.md#现在该用哪些服务)里,不重复在这里。

价格与模型标识**刻意没有**抄进仓库:它们会变,而一份没人复核的数字比一个链接更糟。

### 中继,以及验证了什么

[`tools/passport_bridge.py`](../../../tools/passport_bridge.py) 实现了
[`bridge-protocol.md`](bridge-protocol.md) 里的协议,**除标准库外没有依赖**,并带一个不需要密钥的
`--fake` provider,所以设备侧**不花钱就能检查**。在真机上逐端点验证:

```text
POST /voice      <- 92160 字节、2.9 秒音频,录制过程中边录边传
GET  /speak      <- "hello from the bridge",而设备把回来的东西播了出来:
                    last="spoke 31 KB (16000 samples)" —— 16 kHz 下一秒,正是发过去的那个音
GET  /work-status <- 工作屏的那份文档,主机取过,设备的轮询也在取
```

转写本身返回的是 fake provider 的固定文本;**唯一还没在这个中继上看到的一环是 `/voice/transcript`
轮询**——一次真实的回合在它之前就被静音闸拦下了,那就是下一点。

### 一次真实回合还需要什么

一个人。当我驱动一次按住说话、但**没有对着它说话**时,设备的表现完全符合设计:

```text
last="90 KB, peak 369 below gate 942: discarded"
```

它**在录音的同时就把音频传了出去**——所以中继收到了 2.9 秒的房间底噪——然后在测到峰值远低于房间底噪
两倍之后,**把这个回合丢掉了**,而不是把一个它知道是空的问题发出去。这是正确的行为,同时也正是
**没有人在场就无法验证的边界**:一个人在这个麦克风前的说话电平,不是测试能制造出来的东西。

## 2026-10-15 —— 第 38 次会话：工作屏不再把主人拽回去,而页面可以从设备自己检查了

主人的两条报告。一条是我自己搞的乱;另一条是真 bug——而第一条其实**也是我搞的乱**。

### "为什么它一直在 index repo?"

因为**我在这台机器上留着一个替身桥接服务,还把设备指了过去**:它的固定状态文档永远写着
`indexing repository`、42%,而设备每五秒轮询一次。已停掉,并清除了设备的 `bridge_url`。

但这条报告的价值超过清理本身。**工作屏过去对每一份文档都接管屏幕,而不只是变化的文档**,所以**离开它
是留不住的**:按 OK 回主页只能撑到五秒后的下一次轮询,如此永远循环。一个整个下午都报同一个任务的桥接
服务,会让这台设备**没法当成别的东西用**——这正是主人看到的。现在它只在这份文档**说了新东西**时才接管
屏幕(任务、状态、问题、或选项数量),同时仍然刷新屏幕上的内容,所以**看它的时候永远是最新的**。

真机验证:第一份文档接管屏幕;回主页后**重复的同一份文档不再把它拽走**;换成**不同的**文档则再次接管。

### 页面现在可以从设备自己检查了

`prov start` 报告接入点已起,但"**页面到底有没有在被服务**"这个问题,过去仍然需要同一网络上另一台机器
才能回答。现在不需要了:

```text
prov fetch /            -> HTTP/1.1 200 OK,响应体以页面的 doctype 开头
prov fetch /api/status  -> HTTP/1.1 200 OK
```

`prov fetch` 向**设备自己的控制台**开一个套接字(先试接入点地址,再试回环),发一个 GET,打印状态行与
响应体开头。**失败现在只可能是设备自己的问题**,而成功意味着**任何能到达该地址的客户端都会拿到页面**。
这正是主人两次会话之前要的那种自测,用在了**最后一个还依赖别人网络的问题**上。

### 主人的浏览器还需要知道两件事

页面**在配网门户运行时才存在**;在一台已经配置好的设备上,门户是在**进入配网模式**时启动的——长按 UP
后出现的信息屏现在就是这么写的。**常开控制台**被考虑过,并基于**实测**被否决:HTTP 服务运行时,剩余连续
内存**不足以**让语音通路需要的 TLS 会话成立,这个取舍在冲突第一次被测到时就被记录下来了。

第二件事是浏览器而不是设备:这里在 80 端口上提供**明文 HTTP**,而浏览器越来越多地**先试 `https://`**,
所以地址前面必须写上 `http://`。

## 2026-10-15 —— 第 37 次会话：那个页面从来没有被服务过,而角落现在会说出来

主人问了两件事:设备现在的地址是多少;以及在一台已联网的设备上长按 UP 时,**先显示当前网络、它的地址和
网页地址**,并把"进入配网模式"变成**一个选择**而不是一个后果。

回答第一个问题,找到了"我连不上"的**第三个真实原因**。

### 那个设置页从来没有被服务过

配网门户的 HTTP 服务**启动失败**,而且**没有任何地方告诉主人**:

```text
配网启动:5/6 HTTP 服务 (ESP_ERR_HTTPD_TASK)
E passport_prov: HTTP 服务启动失败: ESP_ERR_HTTPD_TASK
```

`ESP_ERR_HTTPD_TASK` 意味着服务的任务创建不出来——**没有连续内存放它的栈**。那个栈是 8192 字节,而这**不是
一个决定**:那是从示例里抄来的数值。等到它运行时,入网二维码的像素**已经被预留**(必须如此,否则之后放不下),
于是设备**手里抱着几十 KB,却还要再要八 KB**,然后失败。

**后果比错误本身更糟**:接入点升起来了,屏幕上显示二维码和密码,而**那些凭据通向的页面根本没有被服务**。
主人报告的每一个症状都由此而来。**从像素缓冲被加进去那天起,这台设备就一直在往这个坑里走。**

修法是让两者都放得下:服务栈改为 **5120**(这些处理函数只是把页面渲染进一个堆缓冲、并应用一次表单,不递归),
入网二维码的静默边从规范的 4 个模块改为 **2 个**,又省下 5 KB 像素。静默边由 `prov pixels` **报告给控制台**,
所以对绘制符号的检查知道该期待什么——而在 99 像素下,它**依然与编码器逐格一致**。

启动序列里加了步骤追踪,这正是**一次运行就定位**而不是靠猜的原因:

```text
配网启动:1/6 开始 ... 4/6 热点配置已下发 (ESP_OK)
配网启动:5/6 HTTP 服务 (ESP_ERR_HTTPD_TASK)
```

`prov status` 现在报 `access point: up`,`wifi status` 则报出页面地址**以及此刻是否正在被服务**——因为
"页面不在"和"网络不在"是**两个不同的问题**,而设备应该说清它是哪一个。

### 长按现在会显示信息

```text
气泡:  网络 murez_2.4GHz
       地址 192.168.3.75
       网页 http://192.168.3.75/
提示行: OK: 进入配网模式   DOWN: 取消
```

在一台能正常工作的设备上长按这个键的人,**通常想要的是地址,而不是重新配网**,所以逼他先进配网屏才能读到它
——还要为此升起一个热点——是把顺序搞反了。真机验证:上面三行出现、OK 打开配网屏、DOWN 恢复正常提示并留在
主页、**二十秒后问题过期**。

### 关于这个环境的一点说明

本次会话大部分时间里,这台主机都能访问 192.168.3.75 并取回它的设置页。到最后不能了:`ping` 设备自己的
网关,得到的是**主机自己**回的 "destination host unreachable"——也就是说**主机**失去了到 192.168.3.0/24 的
路由。这是这台机器网络上的变化(它装了好几个虚拟网卡,包括 VPN 客户端),**不是固件能影响的东西**。之所以
记下来,是因为局域网页面**先前被验证过可用**,而最后无法复验的原因是**环境,不是回归**。

## 2026-10-15 —— 第 36 次会话：角落里显示网络,而重新配网会先问一句

主人要的两处改动,都关于**在问题被问出来之前先回答它**。

### 右上角：Wi-Fi 与电量

角落现在回答"从口袋里瞄一眼"该回答的两个问题。`wifi` 是一个词,`wifi_bar0` 到 `wifi_bar2` 是**按关联信号
点亮的三个格子**——高于 −67 dBm 亮三个、高于 −80 亮两个、再低亮一个、完全没有关联则一个都不亮——紧挨着
本来就有的 `battery`。为此新增了 `passport_wifi_rssi()`,它**按需向驱动读取**,因为角落里一个过期的信号值
比没有更糟。

格子做成对象而不是字形,是因为这套界面没有图标字体:**三个矩形换颜色比一个字体便宜**,而且它们有名字,
所以控制台能像看别的一切一样看到它们。

在设备上把链路拿走再还回来验证:

```text
wifi disconnect -> ui get wifi  text: --        battery 98%
wifi connect    -> ui get wifi  text: WiFi      battery 98%
```

指示灯大约每秒刷新一次,有自己的节奏:**关联与信号不会按电量那五秒的节拍变化**,而一个在链路已经起来之后
还说五秒"connecting"的角落,是一个会撒谎的角落。

### 重新配网会先问一句

长按 UP 过去会无条件打开配网屏。在一台**已经联网**的设备上,那几乎肯定是误触——它会升起热点、把入网二维码
放到屏幕上——所以现在它会先问:

```text
ui key up long -> hint  "OK: 重新配网    DOWN: 取消"
                  bubble "已连接 murez_2.4GHz。要重新配网吗?"
ui key ok click -> screen setup        (已确认)
ui key down click -> 恢复正常提示行,仍在主页   (已取消)
沉默 13 秒        -> 恢复正常提示行,仍在主页   (已超时)
```

**没有配置网络的设备会跳过这个问题**,因为对它来说配网屏是唯一的前进方向,一句确认只是噪音。这个问题在按键
处理里**排在"按住说话"之前**,所以按 OK 是回答它而不是开始录音;它还会在**十二秒后过期**,于是一个没人回答
的问题**不会把界面留在一个既不是正常、也不是配网的状态**。

### 控制台工具

## 2026-10-15 —— 第 35 次会话：热点被 station 撞掉了,而配网现在可以走局域网

**主人的报告:** 还是连不上。以及一个值得照做的要求:*需要什么固件就自己写,给自己一个测试联网的办法,
而不是依赖我。*

### 第二个真实原因——因为去找它才被发现

`passport_wifi_init()` 每次调用都强制 `WIFI_MODE_STA`。`passport_provision_start()` 也调用它,所以热点在
那个特定顺序下活了下来——但**station 的每一次重连也会调用它,而切成"纯 station"会停掉正在运行的接入点**。
设备在 station 掉线时会自动重连,于是"打开配网屏 → 手机开始关联 → 路由器打个嗝 → station 重连"这一串动作
**会在手机握手中途把热点从空中撤掉**。手机把它报告成密码错误,因为它没有更好的说法。

Wi-Fi 层现在会先问驱动当前是什么模式,**有热点在运行就保持 `WIFI_MODE_APSTA`**,不再强制纯 station。
用这件事本身验证:

```text
wifi disconnect   -> access point : up, mode : station + access point
wifi connect      -> access point : up, mode : station + access point, agreement : the radio matches the screen
prov events       -> 初始启动之后没有任何记录:没有一次接入点停止
```

### 主人要的那些诊断

- **`prov status`** 现在打印驱动的模式,并把接入点的配置**从驱动里读回来**,报告电台与屏幕是否一致。
  "密码不对"是关于**电台**的陈述,所以答案必须来自电台。
- **`prov events`** —— 最近八条接入点事件(带运行时刻),而且**每一次客户端离开都带 Wi-Fi 原因码并写明含义**:
  "4-way handshake timed out: the password did not match"与"client left on its own: often no internet on
  this network"、以及"**根本没有尝试**"是三件不同的事。它保存在环形缓冲里,所以**没人在看的那个时刻发生的
  尝试,事后仍然读得到**。
- **`prov clients`** —— 此刻谁关联着,信号多少。
- **`prov selftest`** —— 以及一处更正。第一版会扫描自己的热点,扫不到就宣布"NOT on the air"。
  **电台收不到自己发的东西**,所以自扫描**永远看不到自己正在托管的热点**:那个结论是无效的,现在这条命令
  会说明它**能**证明什么、**不能**证明什么。真正能证明接口已经起来的,是驱动自己的
  `WIFI_EVENT_AP_START`——而事件日志现在会记录它;先前那个在 `esp_wifi_set_config()` **之后**才注册的
  处理函数把它漏掉了。

### 走局域网的配网方式——完全不需要新固件

最有价值的证据来自**换一个方式问设备**:Web 控制台**在 station 接口上也应答**,不只在热点上。从与设备同网
的这台主机上:

```text
http://192.168.3.75/            HTTP 200, 3380 字节   完整的设置页
http://192.168.3.75/api/status  HTTP 200  {"wifi":"connected","rssi":-43,...,"largest_block":10752}
```

所以**同一网络上的任何手机或电脑都能配置这台设备**,不需要热点、不需要二维码、也不需要敲密码。
现在这是"我连不上它"的**第一种标准答案**。

### 本次会话做不到的事,直说

**当那个 Wi-Fi 客户端。** 这台机器**只有一块无线电台**,它的电台状态是 `Software Off`,而打开它需要本次
会话没有的管理员权限——尝试被拒绝了。所以最后一里路、"手机真正关联上来"仍然需要一个人。设备侧已验证的是:
接口确实被拉起(驱动自己的事件)、模式是 station + 接入点、地址 192.168.4.1、信道 6、认证是 WPA2-PSK,
以及**电台配置与屏幕逐字符一致**。

## 2026-10-15 —— 第 34 次会话："密码不对"其实是一次崩溃,而不是密码

**设备主人报告:** 手机提示 Wi-Fi 密码不对,连不上。

**不是密码的问题。** 在设备上,`prov start` 直接中止了:

```text
E esp_netif_lwip: esp_netif_new_api: Failed to configure netif (config or if_key is NULL or duplicate key)
assert failed: esp_netif_create_default_wifi_ap wifi_default.c:408 (netif)
```

**问题所在。** `passport_provision_start()` **每次调用都创建**热点的网络接口,而
`passport_provision_stop()` **从不销毁它**。于是**第二次**打开配网屏时,
`esp_netif_create_default_wifi_ap()` 被用在一个**已经存在**的接口上——而这个函数**不返回错误,它
断言并让设备重启**。配网屏此时已经把热点名、密码和入网二维码都画出来了,所以从主人的角度看:**设备在
广播一个网络、二维码看着也没问题,而手机就是连不上**。手机把这件事报告成"密码不正确",因为那是用户
唯一能据以行动的说法。

这与第 31 次会话发现的那个缺陷**属于同一类,而且在同一个文件里**:**每次调用创建、每次调用释放的状态,
其中一侧没有写**。上一个是栈,这一个是网络接口。

**修法。** 页面缓冲与网络接口**只创建一次**,并在整个运行期保留;接口不再在 start 时重建,也不再指望
在 stop 时消失。用那段原本会让它中止的序列验证:

```text
prov start -> access point : up
prov stop
prov start -> access point : up
prov stop
prov start -> access point : up
```

**没有断言、没有寄存器转储**,而且每一轮之后热点都是 up。

**控制台现在能直接回答这个问题。** `prov status` 会把配置**从 Wi-Fi 驱动里读回来**并与屏幕显示的
内容比对——因为"密码不对"是关于**电台**的陈述,而不是关于本应用那些字符串的:

```text
access point : up
ssid         : Passport-91E1
password     : <十个字符,显示在设备屏幕上>
radio        : ssid "Passport-91E1" password "<同样那十个字符>" auth WPA2-PSK channel 6
agreement    : the radio matches the screen
```

**而且密码再也不会被看错。** 它过去是八个十六进制数字,其中包含**两次** `1`——最容易被误读成 `l` 或
`I` 的字符——而这是**一个人从 240 像素屏幕上照着敲**的东西。现在它是十个字符,字母表里**去掉了 i、l、
o、0、1**,既更好敲也更强(31^10 对 16^8)。推导逻辑搬进了 `passport_identity.c`,那是**纯的、有宿主
测试的**:测试断言长度、断言每个易混字符都不出现、断言**同一块板永远得到同样的凭据**、以及相邻 MAC
地址不会得到相邻密码。

**未验证,而且恰恰是主人最关心的那一件事:客户端到底能不能关联上来。** 这台机器的无线电台处于
**软件关闭**状态,而打开它需要本次会话没有的权限,所以本机无法充当测试客户端。电台配置、认证方式、信道
以及与屏幕的一致性都已在设备上确认;**关联本身需要一部手机。**

## 2026-10-14 —— 第 32 次会话：入网二维码在两个层面都验证过了

**里程碑：** 设备绘制的二维码已经**对着一个独立实现逐格核对**,而它绘制的**像素**也**对着自己的编码器**
核对过。**剩下的只有相机。**

### 符号本身

`tools/check_device_qr.py` 读取 `prov qr` 打印的矩阵,用 `qrcode` 包对同一载荷生成全部八种掩码的符号,
再逐格比较:

```text
device: version 3, 29 modules, states mask 2, matrix 29x29
MATCH: the matrix is the reference symbol for fixture 'v3_wifi' under mask 2,
       which is the mask the device states
```

掩码是最值得说清的部分,而**说清它到底证明了什么、没证明什么**很重要。它**没有**说明哪一个掩码"应该"
胜出——那件事从来没有独立裁判,因为当初试用 `segno` 包时,它在填充字节上与规范不一致。它说明的是:
设备绘制的矩阵,在**设备自己声称的那个掩码**下,对那个载荷是一个**合法符号**——而这个性质独立实现能够
确认。**声明与绘制是一致的。**

载荷来自 `make_qr_fixture.py`,那是它被记录的**唯一**地方,所以没有新增任何东西;而抓取到的矩阵
——它携带热点密码——**从不入库**。

### 画出来的像素

**一个正确的符号仍然可能扫不出来:把两种颜色对调,矩阵逐格完美,而任何相机都读不出来。** 只有像素能
说明这件事。因此 `prov pixels` 在**真正被绘制过**的缓冲里对每个模块的中心取样,再与编码器的矩阵比较:

```text
prov pixels: 111 px, scale 3, 37 modules, quiet zone 4
prov pixels: 419 of 1369 module centres are dark (31%), 0 disagree with the symbol
prov pixels: MATCH - the drawn pixels are the encoded symbol
```

它还并排打印左上 7×7 的**绘制值**与**编码值**——正是这一眼让下面那次失败变得一目了然。暗色占比读出来是
画布的 31%,对一个"大约一半是暗"的符号来说看着不对——**而它是对的**:画布包含四模块的静默边,占 1369
个中心里的 528 个且全部为亮。**符号区域本身是 49.8% 暗**,正是二维码应有的样子。

### 先是检查器错了

第一次运行报告 1369 个中心里有 428 个不一致。角上的对照打印显示绘制出的定位图案**恰好偏移了两个模块**,
原因在**我的检查器**而不在固件:它把静默边硬编码成 2 个模块,而应用里是 **4**。现在由**应用把静默边
报告**给控制台,而不是控制台自己留一份拷贝。

这在本项目里是**第三次**由"检查器自带一份常量拷贝"造成的假失败——另外两次在第 30 次会话,而其中一次
是一个关于 ESP-IDF 的错误结论,它还进了协议文档。这个模式足够稳定,值得命名:**自带常量拷贝的检查器
检查的是它自己的拷贝,而不是固件。** 三次的补救办法都是**去问拥有那个值的组件**。

### 未验证,而且现在是一个很窄的问题

**手机能不能读出这块面板上的二维码**——对比度、240 像素宽屏幕上的尺寸,以及玻璃对光做了什么。
**到玻璃为止的一切,现在都被核对了两次**:一次由独立实现,一次对着设备自己的渲染器。

## 2026-10-14 —— 第 31 次会话：一次验收走查,抓出一个崩溃和另外三个缺陷

**里程碑：** 像人一样把界面走了一遍,而它**现在还经受不住这一遍**。四个缺陷,其中一个会崩溃,现在都已修复并验证。

### 1. 长按 UP 触发栈保护错误

那个打开配网屏的手势**每次都会让设备重启**:

```text
Guru Meditation Error: Core 0 panic'ed (Stack protection fault).
Detected in task "passport_input"
```

**这是我自己的回归。** 第 27 次会话我把按键任务的栈从 12,288 削减到 6,144,理由是"二维码编码器已经在
应用工作线程上,它只负责入队事件"。**这个理由错了**:长按 UP 那条分支仍然调用
`passport_app_show_setup()`——它构建屏幕、编码入网二维码、需要约 6 KB。**削减拿掉了空间,却把调用
留在了原地。**

现在那个屏幕上一切"重"的工作都在工作线程上完成——按键任务只设一个标志,工作线程负责预留像素、启动热点、
构建屏幕。**同一个错误在这次修复里犯了两次**:第一次尝试把 `qr_reserve()` 挪进了按键分支,等于把编码器
又放回同一块小栈上,于是以完全相同的方式崩溃。这一点值得记成**规则**而不是轶事:**按键任务的栈是对该
路径上每一个调用的约束,必须在添加调用时检查,而不是在它崩溃之后。**

### 2. 入网二维码不再渲染

配网屏终于能打开之后,它显示的是失败文案而不是二维码。像素需要 **24,642 字节**,而**先启动的热点**会
占掉几十 KB 并打碎剩下的空间。

修法是在**请求该屏幕的瞬间、且在热点启动之前**预留像素,屏幕关闭时释放。这就是最初的预留,连同它的
理由一起恢复——**分配失败时二维码无法重试,所以它必须先来**——只改了**持有时间**。终生持有时,这些字节
让 TLS 会话没有空间,而那个代价正是第 27 次会话发现的。

```text
passport_app: 二维码缓冲已就绪:24642 字节(111 像素)
passport_app: 二维码已生成:版本 3,29 模块,缩放 3,111 像素,载荷 40 字节
```

### 3. 中文文本用了没有中文字形的字体

四个标签——主页提示行,以及配网屏和工作屏上的三个——用 Montserrat(拉丁字体)创建,却承载中文文本。
**在玻璃上它们是空方块。** 仓库自己的指南正好警告过这一点,并且明说"构建成功什么也证明不了";
缺的是一个**在设备上检查它**的办法。

现在有了。`ui audit` 遍历每一个屏幕,对**每一个含非 ASCII 字符的标签**,向它**实际使用的字体**询问该字符
是否存在。做成运行时检查而不是源码审查,是因为这两个事实**住在不同的地方**。

**它在修复之前跑过,而且失败了**——这是它值得信任的唯一理由:

```text
MISSING: passport/hint can not draw U+63D0, so "OK:提问    长按OK:待机" has holes
ui audit: 5 labels checked, 1 with characters their font cannot draw
```

修复后:三个屏幕合计 **0 处问题**(主页与工作屏 15 个标签,配网屏 11 个)。

### 4. 屏上提示描述的是已经不存在的操作

它仍然写着 `OK:提问  长按OK:待机`——那是 OK 变成"按住说话"、待机移到"双击 UP"之前的版本。
**会撒谎的提示比没有提示更糟,因为它教的是错的手势。** 现在它写的是 按住OK说话 / 长按DOWN工作 /
长按UP配网 / 双击UP待机,而且用的是**画得出这些字的字体**。

### 另外观察到的、且是正确的一件事

走查早期,一次注入的手势被**静默吞掉**了。因为静置超时后屏幕已进入熄屏,那次按下被当作唤醒消费掉、
不再做别的事——正是第 25 次会话的仲裁在正常工作。它浪费了我一分钟;记下来是因为**真人也会遇到同样的困惑**。

### 未验证

**手机能不能读出玻璃上的那个二维码。** 门户开着时最大连续空闲块只有 7,680 字节,连一张它的快照都分配
不出来。设备生成的**矩阵**可以用 `prov qr` 打印出来,因此**符号本身**可以对着同一个载荷的独立实现来核对
——只是这个环境里没有装解码器,而安装它不是本次会话该做的事。这是下一件事。

## 2026-10-14 —— 第 30 次会话：静音阈值改为实测房间,并撤回两份错误的缺陷报告

**里程碑：** 设备在启动时**测量自己所在的房间**,并据此设定静音阈值。而上一轮我报告的两个缺陷**其实都
不存在**——这是本次记录里更重要的一半。

### 撤回

**"按下之后约 1.4 秒才开始录音。"** 并不存在。为此专门加了仪表,测得:

```text
延迟: 按下->唤醒 0 ms, 唤醒->界面 0 ms, 界面->连接就绪 26 ms
```

**从按下到第一个采样是 26 毫秒。** 第二次检查用的是真实使用场景——**300 毫秒的短按**——录到 11,520
字节,即 16 kHz 音频的 0.36 秒。**录音与按键时长是吻合的。** 那 1.4 秒来自我的测试脚本:它写入命令、
等满一个固定读取窗口、再发松手,而我把由此得到的空录音**读成了固件故障**。

**"静音门限默认值落在环境区间之内,会丢掉真实语音。"** 也错了,而且错在相反方向。本次环境峰值在多次
运行间从 216 到 886 不等,而**"语音"从来没有被真正测过**——所有自动化测试都是在控制台敲字,没人对着
它说话。所以固定的 400 并没有丢掉语音;它只是一个**猜测**,滤掉安静的时刻、放过嘈杂的时刻。

### 真正的问题,以及处理方式

**固定阈值是对一个没人测量过的房间的猜测。** 启动预热——那半秒采集本来只是为了让编解码器稳定下来
——现在**顺便测量房间**,并跳过它自己的稳定瞬态;门限取实测峰值的两倍,钳制在 300 到 4000 之间。控制台
可以钉住一个数值,0 则关闭这项检查。`voice status` 会报告这个数字**以及它的来源**。

真机验证:

```text
voice gate -> state=idle mic=closed turns=0 gate=562 (twice the measured room)
一次安静按下 -> 48 KB, peak 252 below gate 562: discarded
```

启动时测得房间峰值 281、门限算出 562,而**一次不含语音的按下被丢弃**——阈值第一次就完成了它的工作,
而且是在它被测量的那个房间里完成的。做出判断时音频**已经发出去了**,所以省下的是**服务商调用**而不是
流量;这一点写在代码里。

**仍未验证、而且我无法验证的是:** 对**一个人对着这个麦克风说话**而言,这个门限设得对不对。代码里把
余量明确写成**启发式**而不是调优值,因为说话音量只有人才能测。那个覆盖入口正是为此存在。

### 把这个模式说出来

**这是连续第二次**:我发布的固件缺陷其实是**我自己测量方式的产物**。两次形状相同——结论是从测试脚本的
行为**推断**出来的,而不是来自设备报告的数字。因此我现在采取(而不是承诺)的对策是:**先加仪表,再下结论。**
凡涉及延迟或电平,设备都会**先把测量结果记录下来**,之后才允许得出结论;而且**仪表会留下来**——按下到
首个采样的分解之所以留在固件里,正是因为它就是**那个把问题定论掉的数字**。

## 2026-10-14 —— 第 29 次会话：回答会说话了,同时更正一处错误诊断

**里程碑：语音环路完整了。** 按住 OK、说话、松手:音频流式送到桥接服务、转写返回、模型回答,而且
**回答通过扬声器播放出来**——整个语句期间**麦克风可证明是关着的**。

### 已构建的内容

`GET <bridge>/speak?text=…` 以原始 PCM 返回朗读音频,**与设备上传的格式相同**,因此一个形状覆盖两个
方向。设备边收边送进扬声器,而音频通路由新的 `passport_audio_play_begin/_chunk/_end` **为整段语句只
取一次**。这个细节正是重点:用一次性调用逐块播放,会在**一个回答内部**把仲裁器交还几百次,从而给采集
留下缝隙——而那正是这条不变量存在的理由。

长回答只朗读**前一段**——约 190 字节,在字符边界处截断。一千字节中文就是半分钟音频,而百分号编码会把
它承载的内容放大三倍;完整文本在屏幕上,被截短时日志会说明。回答是中文,所以查询串需要一个百分号编码器
——它现在是一个**带自己宿主测试的纯函数**,包括"截断的编码会被拒绝,而不是以裸 `%` 或 `%E` 发出去"。

### 真机验证

```text
按住、说七秒、松手
  松手:361 个分块, 231040 字节
  桥接服务: POST /voice -> 231040 bytes of PCM (7.2 s at 16 kHz)
            GET  /voice/transcript -> ready=1
  转写: which branch should I deploy
  桥接服务: GET /speak -> text='I can help you figure out which branch to deploy,
            but I need a bit more context. Could you share: ...'
  audio status: owner = playback, microphone = closed (playback holds the path)
  之后:        state=idle, owner=free, microphone=allowed, 46248 B 可用 / 32768 最大块
```

中间两行就是整个功能:**模型自己的回答被请求为语音**,而在它播放期间,仲裁器持有通路、麦克风关闭。
最后一行是这一回合干净收尾、不留下任何东西。

### 我欠这个项目的一处更正

第 27 次会话得出结论说这个 HTTP 客户端"在分块上传之后读不到回答",第 28 次会话围绕它构建了一套协议。
**那是错的。** `esp_http_client_fetch_headers` 返回的是一个**长度**——正的内容长度、chunked 时为 0、
出错时为 -1——而代码把它与 `ESP_OK` 比较,于是**任何带响应体的响应都看起来像传输失败**。客户端没有问题。

值得记录的**不是这个 bug,而是这个错误的形状**:一句听起来很合理的"别人代码的限制"被接受了,还写进了
契约,而它唯一的证据是一行**由我自己的类型混淆所产生的日志**。代码注释、协议文档与进度日志现在都改成了
实际发生的事。两次请求的设计被保留——**要花几秒转写的桥接服务不该被逼着占住上传的套接字**——但保留它
靠的是它自身的价值,而不是一个从未存在的缺陷。

第 27 次会话的**第二个** ESP-IDF 观察依然成立且已验证:客户端声明分块请求体,却把调用方的字节不加框架
地写出去。

## 2026-10-14 —— 第 28 次会话：语音这一轮,端到端跑通了

**里程碑：** 按住 OK、说话、松手——回答回来了。音频流式送到桥接服务,转写返回,模型被询问,回答显示在
屏幕上。**回答还不会朗读**,那是语音里程碑唯一还缺的一块。

### 卡住的那个缺陷是怎么清掉的

第 27 次会话结束时留下的失败很具体:上传逐字节准确到达,而客户端读不出回答。修法**不是跟客户端较劲,
而是用两次请求**。上传变成"发完不管",转写照本项目取别的一切东西的方式取回:一个**普通 `GET`**,
而工作模式早已在这台设备上证明了这条路可用。两端都在我手里,所以**协议是围着传输的弱点塑形的**,
而不是反过来。理由写进了[桥接协议](bridge-protocol.md),免得将来的读者"顺手"把它简化回一次请求。

第一次尝试随后以一种值得记录的方式失败:桥接服务回答 `{"ready": true, ...}`,而设备轮询六次后放弃。
设备的读取器是**整数读取器**——工作文档用的同一个——所以 JSON 布尔值根本不是它能看见的值。现在
**缺少 `ready` 视作已就绪**(宽容的方向是对的),并且协议规定该字段为 `1` 或 `0`。教训在**接缝**上,
而不在解析器上:两个组件可以就协议达成一致、却在类型上不一致,而**只有端到端跑一次才能发现**。

### 真机验证

```text
voice hold -> 说七秒 -> voice release
  语音任务日志(中文): 松手:352 个分块, 225280 字节, rms=366 peak=886
  语音任务日志: 音频已送达(220 KB),去取转写
  语音任务日志: 转写:which branch should I deploy
  voice status: state=idle, transcript="which branch should I deploy",
                last="turn finished: said ..."
  桥接服务日志: POST /voice -> 225280 bytes of PCM (7.0 s at 16 kHz)
                GET  /voice/transcript -> ready=1
  模型回答: 1023 字节,2796 ms
```

随后又跑了**第二个回合**来证明第一个真的结束了:261 个分块、167,040 字节,`turns=2`,状态回到 `idle`。
之后内存读数 48,612 字节可用、最大连续块 34,816——**一个回合不留下任何东西**。

### 这次运行暴露的缺陷——真实存在,且尚未修复

**按下之后约 1.4 秒才开始录音。** 这一回合先开麦克风、更新屏幕、连上套接字,然后才读第一个采样;而这
比听上去要长:**短按会什么都录不到**——本次会话里好几次运行正是这样,原因在被理解之前一直是个谜。
修法是**立刻开始采集**,把开头那一小段先放进一个小预缓冲,连上之后再冲出去——现在内存够了,设计也就
几行代码。但它**没有做**,所以一个人按下后立刻开口,会丢掉句子开头。

### 还有一点必须说明

静音门限的默认值 400 **落在**这个房间的实测区间**之内**:这几轮里环境峰值测到 366 到 671,而说话是
886 到 1,821。**一个落在环境区间中部的门限会丢掉真实语音。** 本次所有测试都用 `voice gate 0` 绕过了它,
所以这个默认值**没有经过真实使用检验**,应当从一次正式测量重新推导,而不是再猜一次。

## 2026-10-14 —— 第 27 次会话：按住说话把音频流式发出去,顺便抓出一个内存回归

**里程碑(部分)：** 按下时麦克风打开,说话在**仍被录音的同时**流向桥接服务,桥接服务确认了确切的字节数。
**把转写读回来还不成功**,那是唯一剩下的一件事。

### 已构建的内容

`passport_speech` 拥有音频与套接字;**回合规则仍留在 `passport_voice`**,它本来就是纯逻辑且有宿主测试。
按下打开麦克风,抬起结束这一回合;OK 现在是**按住说话**而不是文本回合——**一个按键一个含义**。深睡
移到**双击 UP**,因为"按住 OK 说话"和"按住 OK 睡觉"不可能同时成立。

录音是**边录边流**:20 ms 一个分块,从编解码器读出来就写进请求体,所以**没有任何缓冲区持有整段话**。
这不是优化。几秒语音就是几十 KB,而设备没有这些内存;其他方案都在 `passport_speech.h` 的头注释里被
否决了,包括看起来最简单的那一个——**录成有界缓冲、按 WAV 上传**——因为 WAV 需要把长度写在前 44 字节里,
而"长度未知的录音"恰恰没有这个长度。

采集期间测量房间本身的电平,低于阈值的录音被当作空房间:**丢弃转写而不去请求**,省下一次服务商调用。
阈值可以从控制台调整,而且它**确实需要调整**——见下文。

### 真机验证

```text
voice hold / voice release,按住三秒
  passport_speech: 录音开始: held=1
  passport_speech: 第一个分块: capture=ESP_OK held=1
  passport_speech: 松手:213 个分块, 136320 字节, rms=401 peak=1005
  桥接服务日志:    POST /voice -> 136320 bytes of PCM (4.3 s at 16 kHz)
```

字节数才是关键检查:213 个 640 字节的分块正好是 136,320;而 136,320 字节的 16 kHz 单声道就是 4.3 秒,
与按键按住的时长一致。**音频确实在仍在被录的时候离开了设备。**

### 内存回归——比这个功能本身更要紧

测试过程中 `llm ask` 开始以 `ESP_ERR_HTTP_CONNECT` 失败。**不是网络问题,设备快没内存了:**

```text
[mem] free=4972 B  min=40 B  largest=1664 B      ← 修复前
[mem] free=50428 B min=43544 B largest=38912 B   ← 修复后
```

两个原因,**都是我自己造成的**。**32 KB 的二维码像素在开机时被预留、并终生持有**,理由是"预留能保证
入网二维码渲染一定成功"。那份确定性**代价超过了它的价值**:缓冲被持有期间,静置时的最大连续空闲块只有
7,680 字节,**TLS 会话已经完全分配不出来**。现在像素在配网屏打开时分配、关闭时释放——这个做法之所以
成立,恰恰因为**配网与服务商调用从不需要同时发生**。第二个原因是**我此前为了追查更早的故障而防御性
抬高过的四个任务栈**,现在回到它们真正需要的尺寸。

修复由**它弄坏的那件事**来验证:一次完整的模型往返恢复,证书校验通过、492 字节回答、耗时 1,759 ms。

### 两个"撞了南墙才学到"的 ESP-IDF 行为

- **`esp_http_client` 在以负的写入长度打开时会声明 `Transfer-Encoding: chunked`,然后把调用方的字节
  *不加分块框架*地写出去。** 于是请求体的头几个字节被服务器当成"分块大小"来读。它之所以被发现,是因为
  本项目的替身桥接服务会**记录自己解析不了的东西**,而它记录下来的正是录音的头几个采样。现在分块框架由
  调用方自己拼,理由写在代码旁边。
- **分块上传之后,客户端读不到回答**:`fetch_headers` 报传输失败,直接读数据也返回空,**尽管服务器已经
  回答了**。桥接服务已被证明是好的——手工构造一个分块请求打过去,它返回 `200` 与那段转写。这就是那个
  尚未修复的缺陷。

### 还没成功的地方,以及它到底卡在哪

转写始终没有到达,所以模型从未被询问,这一轮语音对话**还不完整**。已验证的是**本来存疑的那一半**——
采集、流式发送、逐字节准确送达;而失败现在是一个**具体且可复现**的问题,落在一个**已被双向测试过的
边界**的一侧。

## 2026-10-14 —— 第 26 次会话：Web 后台覆盖了全部设置,而且不泄露它们

**里程碑：** 设备现在可以**完全用手机配置**。控制台能改的每一项设置,配网页都能改;而且页面在改的
同时显示实时状态。

### 已构建的内容

配网页现在**由解析提交的那同一张表生成**。表里列出每个表单字段、它写入的配置字段、它的标签和它的
分组;页面遍历这张表,解析器也用它来应用。**新增到 schema 却被忘在这里的设置,现在会被宿主测试抓到**,
而不是等一个找不到它的用户来发现。

那张表的测试里有三项检查,也正是这张表值得存在的原因:每一项都指向 schema 里真实存在的字段;没有
两项写同一个设置或共用同一个表单名;以及**这张表覆盖了 schema 里每一个可设置的字段**——是**数出来**
的,不是想当然的。

某个字段是否属于密钥,是**问 schema** 而不是在表里重复一遍,所以一个密钥**不可能因为有人忘了标记
两次而变得可见**。密钥字段渲染成空输入框,旁边标注是否已设置;留空仍然表示"保持不变"。

页面分组为 网络 / 对话模型 / 语音 / 工作模式 / 偏好,并显示实时状态:Wi-Fi、热点、地址、电量、可用
内存,以及指向 `/api/status` 与 `/api/config` 的链接。

### 真机验证

```text
prov page        3,380 字节、完整 HTML、19 个输入框、5 个分组标题
                 页面里既没有已存的 Wi-Fi 密码,也没有 API Key
                 (是拿真实值去比对的,不是用眼睛看的)
prov form pet_name=Whale2&notify_mode=2&idle_off_seconds=30
                 应用并保存;config get 三项都能确认
                 两个密钥仍读作 "(set)":空字段没有把它们清掉
prov page status {"wifi":"connected","rssi":-41,...,"free_heap":21664,"largest_block":11264}
```

### 路上我自己的两个错误

- **控制台的预览被截断,而页面本身是好的。** `prov page` 打印进的是一个 **2048** 字节的缓冲,而
  HTTP 那条路用的是 **4096**,于是预览在中途断掉、页面看起来是坏的。现在控制台用同样的尺寸;教训是
  **一条与真实路径限额不同的调试路径,会凭空造出 bug**。
- **是我"页面是否完整"的检查错了,不是页面。** 我问的是抓到的文本是否以 `</html>` 结尾;它实际以控制台
  提示符 `passport>` 结尾,所以答案是"否"。而渲染器报的是 3,380 字节,footer 其实一直在抓到的内容里。
  这一点值得写下来,因为**错误的检查差点把我送进渲染器里排查**。

我还写了一段确实糟糕的代码然后又删掉了:用 `strstr` 在渲染好的页面里找占位符、再 `memmove` 挪动后面
的字符串来插入电量数字。**在 `snprintf` 之前先把字符串格式化好**,才是它一开始就该有的样子。

### 一个值得进预算的测量

在配网门户运行、且屏幕上有那个二维码的时候,可用堆是 **21,664 字节**、最大连续块是 **11,264 字节**。
页面缓冲与二维码像素**同时**被占着,上面还有热点与 HTTP 服务。后果很具体:**直连模式的 TLS 需要约
24 KB 连续内存,所以门户开着的时候它跑不起来。** 配网与服务商调用**不能重叠**——这在设计上本来就成立
(正在配网的设备还没有什么要对模型说),但它现在是一条**实测约束**而不是假设。

## 2026-10-14 —— 第 25 次会话：待机、深睡,以及它抓出的唤醒电平 bug

**里程碑：** 没人时屏幕会自己熄掉;按键能点亮它,而且**不会顺带执行那颗键本来的动作**;需要时还能深睡。

### 已构建的内容

`passport_power` 负责三件事:

- **静置熄屏。** 超过配置的 `idle_off_seconds` 就关背光;界面继续运行,所以屏幕是**瞬间回来**而不是
  从零重画。超时是**实时读取**的,改完不用重启就生效;**0 表示永不熄屏**,这是出货默认值——负责人
  要的是"先做常连设备"。
- **"唤醒"与"动作"的仲裁。** 待机和应用共用同三个按键,所以屏幕暗下去之后的**第一次按键只负责点亮
  屏幕**,其余动作被吞掉。验证方式是看宠物的表情:它**停在 `idle`**,而屏幕确实亮了。
- **深睡**,长按 OK 触发。入睡前 BSP 会先把按键脚交回**普通数字输入**——ADC 还接管着的时候该脚
  读回是低电平,而那正是唤醒条件比较的值,设备会在入睡瞬间醒回来。

两处拒绝是刻意设计而不是防御性填充:如果请求入睡时**已经有键被按住**,请求会被拒绝并附上导致拒绝的
读数,因为唤醒条件当时就已经成立;如果唤醒源配置失败,设备**不睡**——宁可一台醒着的设备,也不要
一台没人能唤醒的设备。

### 设备抓出的 bug

第一次尝试**立刻醒回来**,看起来像根本没睡。原因在我:BSP 返回的是**什么都没按时**该脚稳定在的电平
(本板为 1,因为按键节点是上拉的),而我按这个电平去配置唤醒,而不是按"按下时产生的电平"。于是唤醒
条件在入睡那一刻就成立了。

这正是 BSP 自己的注释警告过的危险,**只是方向相反**——它警告的是"让 ADC 继续接管会让该脚读回低电平、
从而立刻唤醒",它没有警告**返回的电平是空闲电平**。现在映射已反转,理由写在旁边。

### 真机验证

```text
开机                power: screen=on idle=8s off_after=60s
config set idle_off_seconds 10        (实时：不重启、不保存)
13 秒后             power: screen=off idle=24s off_after=10s
ui key ok click     passport_power: 屏幕已点亮
                    power: screen=on idle=1s
                    宠物表情仍是 "idle":这次按键是唤醒,不是动作
power sleep 20      控制台在一秒左右消失,设备不再应答——这就是深睡从这里看起来的样子
之后                设备重新应答,说明它醒了
```

**是哪个唤醒源把它叫醒的,从这个控制台看不到**,这一点要如实说明而不是猜:打开端口会翻转 DTR 与
RTS,从而复位芯片——观察到的是 `rst:0x15 (USB_UART_CHIP_RESET)`——所以唤醒原因在被读到之前就没了。
"是定时器"这个结论是**推论**:深睡期间 USB 外设已断电、够不到芯片,而且没有任何按键被按下,于是已
配置的定时器是唯一可能的来源。

### 未验证的部分

- **按键唤醒**,那需要一个人去按:长按 OK 入睡,然后按任意键。这正是出货路径,也是本里程碑交到你
  手上的检查。
- **待机电流。** 需要外接 USB 功率计——这在写测量计划时就记录了;**这里不编造任何数字。**

## 2026-10-14 —— 第 24 次会话：工作模式会出声了,而且只在该出声的时候

**里程碑：** 当桌面需要它的主人时,设备会响一声;这个判断只依据那份文档;其余时间保持安静。

### 已构建的内容

`passport_tone` 用整数生成正弦波——没有浮点、没有一堆莫名其妙的数字表、不依赖库。半波上用
Bhaskara 近似再镜像,角度以 **1/1024 度**为单位,并加线性升降沿,避免音符开头结尾"咔"一声。

`passport_notify` 把两三个音符串起来,并**通过既有音频通路**播放,所以提示音和别的东西一样受同
一套仲裁:**播放期间麦克风关闭**。在没有回声消除的板子上,一个会录到自己的通知就是缺陷,而仲裁器
本来就禁止这件事。

**要不要求出声**的判断是纯逻辑,放在 `passport_work` 里——因为这是关于工作状态的规则,而不是关于
音频的:新出现的问题、完成、失败值得打扰人;running 与 idle 不值得;而 `notify_mode` 为 0 就是
无论发生什么都安静。模式 2 要求朗读,而工作模式还没接入语音,所以它作为**一个独立的答案**上报,
设备照旧响一声,同时在日志里说明朗读还没接上——**配置成朗读的设备,应当仍然听得见,而不是对此
沉默。**

两个值得点名的判断:**每五秒一次的轮询绝不能嘀嘀叫**,所以只有"变化"才播报;**开机后的第一份
文档不播报**,因为一个问题可能已经等了几个小时,而开机就响会教会主人忽略这个声音。

### 音频测试找到了生成器里的真 bug

该测试是拿 C 库的正弦**对照**的,所以它量的是**总误差**,而不是这个近似本身的名声。这抓出了一个
公式的声誉会掩盖的错误:角度被量化成**整度**,而在半波两端,仅这一项就让样本偏离真实正弦最多
**1.75%**——比 Bhaskara 自身的 0.16% 差一个数量级。把角度改成 1/1024 度后修好;现在测试断言整个
周期内的最坏误差小于 **0.5%**。

测试还断言了音高(数过零点:1 kHz 在四分之一秒里约 250 次)、音符两端是安静的、**分块填充与一次
填充逐字节相同**,以及各种退化情形:淡入淡出比音符本身还长、零长度音符、超过满幅的振幅、零采样率。

我自己在测试里的一个错误也值得记下:它最初让生成器往一个 **4096** 样本的数组里填 **16000** 个
样本,然后崩了。生成器完全按要求做了;**给调用方的缓冲区定尺寸是调用方的事**。

### 真机验证

```text
notify status   -> buffer=ready, notify_mode: 1
notify test question / done / failed
                -> 每次都 ESP_OK,渲染 4096 个样本
audio status    -> 播放结束后 owner free、microphone allowed
```

然后是实时行为,对着替身桥接服务:桥接服务提供 `running` 任务时,设备轮询了十秒**整段日志里没有
任何提示音**;当桥接服务切到 `waiting`,设备记录下问题提示音,屏幕显示 `Which branch?`。也就是
**它只播报变化**。

### 未验证的部分

**这些提示音听起来对不对。** 生成器被测量过、播放报告成功、仲裁也检查过——但这次会话里**没有人
听过它们**。那是人的检查,和"二维码能不能扫出来"属于同一类。

## 2026-10-14 —— 第 23 次会话：工作模式对接真实服务器,端到端

**里程碑：** 设备从网络上的服务器取回状态文档、显示它,并把回答发回去。**整个环路是对着一个真实的
HTTP 服务器跑通的**,而不是从控制台喂进去的。

### 已构建的内容

`passport_work_client` 在自己的任务上轮询 `<bridge_url>/work-status`,把解析出的视图交给屏幕;并把
所选选项 POST 到 `<bridge_url>/answer`。用明文 HTTP 而不是 TLS,原因与决定放在一起记录:桥接服务
是同一网络上的配套进程,文档不携带凭据,而跳过握手能让**最大连续空闲块保持在 112 KiB 而不是
68 KiB**——这块板子的显示与音频通路需要它。后果也写下来了:**网络上任何东西都能提供文档或读取回答**,
所以在预留的 `bridge_token` 变成真正的认证之前,桥接服务不得离开可信局域网。

协议现在是一份文档而不是一种默契:[桥接协议](bridge-protocol.md),含字段表、设备施加的规则,以及它
刻意不做的事。`tools/mock_bridge.py` 是用于在配套服务存在之前测试的替身服务器——下面的验证就是用它。

### 端到端验证

设备经局域网指向本机上真实的 HTTP 服务器:

```text
config set bridge_url http://192.168.2.183:8080 ; config save
work client   -> polls=2 failures=0 last="fetched, state=waiting"
ui get work_task     -> text: deploy
ui get work_state    -> text: waiting
ui get work_question -> text: Which branch?
ui get work_option0  -> text: > main
```

**没有任何内容是从控制台喂进去的:屏幕自己从网络更新了。** 然后是从按键到服务器日志的回答通路:

```text
work key down  -> 标记移动到 develop
work key ok    -> answer -> develop
work answer    -> ESP_OK, last="answer accepted"
服务器记录到: [{"answer": "develop"}]
```

而且设备会**跟随变化**,不只是取一次。把服务器换一个场景重启后,没有任何命令,设备报告
`last="fetched, state=done"`,屏幕显示 `indexing repository` / `done` / `100%`。

### 备注

- 测试后已清除设备的 `bridge_url`,以免它一直轮询一台已经停止服务的机器。重新设置就是上面那两条命令。
- 替身桥接是**测试辅助**,不是产品的一部分。它被提交,是因为有一份参考实现放在旁边,协议更容易被信任,
  也因为在配套服务存在之前,下一个人需要有个东西可以让设备指过去。

## 2026-10-14 —— 第 22 次会话：工作模式上屏,逐字段验证

**里程碑：** 工作模式现在**看得见、也能用按键操作**。任务、进度、以及带选项的问题都出现在面板上,
按键可以移动并确认选择。

第三个屏幕 `work`,其对象可被控制台读取:`work_task`、`work_state`、`work_bar`、
`work_percent`、`work_question`、`work_option0` 到 `work_option3`、`work_hint`。按住 DOWN 进入,

布局里有三个决定是可见的:

- **未知进度画成"缺失",而不是一个空进度条。** 否则一个不上报进度的桥接服务会让每个任务看起来都

- **选中的选项带标记且有颜色**,这也正是控制台能判断选中的是哪一个的方式。
- **视图住在应用里,而不是控制台里。** 控制台与按键任务都只是同一份状态的薄驱动,所以从控制台喂进去
  的文档,更新的正是按键会更新的一切,两者不可能不一致。

### 真机验证

```text
work feed {"task":"deploy","state":"waiting","question":"Which branch?",
           "option0":"main","option1":"develop","selected":0}
work: state=waiting progress=-1% task="deploy"
ui screen     -> screen work  240x320  children=13
ui get work_percent -> text: --            ← 未知,而不是卡在零
ui get work_option0 -> text: > main
work key down
ui get work_option1 -> text: > develop     ← 标记在面板上真的移动了
work key ok   -> answer -> develop
```

在真机上也验证了"无法解析的文档":喂一份被弄坏的文档时,它报告保留上一份视图,并且
`ui get work_task` 仍然读到先前的任务。**这就是"宁可拒绝也不清空屏幕"这条规则在硬件上成立。**

### 两个发现

**我自己的一处命名不一致。** 选项对象被命名为 `option0`,而屏幕上其余对象用的是 `work_` 前缀,
于是同一个路径可能随"当前哪个屏幕在前面"而指向不同对象。现在该屏幕的每个对象都带前缀:控制台里的
名字**跨屏幕唯一**,`ui get work_task` 只有一个含义。

**非 ASCII 仍然无法从控制台输入。** 一份含中文任务名的状态文档被判为无法解析:控制台的行处理会把

来自网络或语音,而不是控制台。

## 2026-10-14 —— 第 21 次会话：工作模式的文档格式与按键规则,已在真机验证

**里程碑：** 工作模式的**设备侧**已经存在。桥接服务还没写,所以这里验证的是**协议与交互规则**,
不是一次真实的会话。

### 已构建的内容

`passport_work` 解析一份状态文档,并把按键翻译成少数几种回答。

**这份文档是刻意做成扁平结构的:**

```json
{"task":"indexing","progress":42,"state":"running",
 "question":"Which branch?","option0":"main","option1":"develop","selected":0}
```

选项用**编号字段**而不是 JSON 数组。这是与桥接服务之间的**契约**,不是疏忽:设备端的读取器是
几百字节而不是一个解析器,而编号字段**不需要分隔符转义**,所以一个含逗号或引号的 branch 名字
不可能破坏这个列表。最多读四个选项,正是面板能用高亮行显示的数量。

有四个决定被写进代码而不是留给调用方:

- **字段缺失不等于零。** `progress` 缺失读作 -1 并显示为未知;若读成 0,就会声称任务卡在零进度。
  这就是整数读取器要报告"这个键是否存在"的原因。
- **越界的数字是钳制而不是拒绝**:一个拒收 250 的进度条会什么都不显示,那比显示满更糟。
- **选项列表在第一个空缺处结束**,因此孤立的 `option3` 不会单独出现。
- **既没有 task 也没有 question 的文档会被拒绝**,保留上一份视图,而不是把正在显示有用内容的屏幕
  清空。

按键规则:选择会环绕,确认只在"有等待中的问题且它带选项"时才有效,而且**一个问题只接受一个答案**
——再按一次会被拒绝。

### 真机验证

```text
work feed {"task":"indexing repository","progress":42,"state":"running"}
work: state=running progress=42% task="indexing repository"

work feed {"task":"deploy","state":"waiting","question":"Which branch?",
           "option0":"main","option1":"develop","option2":"release","selected":0}
work: state=waiting progress=-1% task="deploy"
work: question="Which branch?"
  > option0: main
    option1: develop
    option2: release

work key down        -> 选择移动
  > option1: develop
work key ok          -> answer -> develop
work key ok          -> nothing to do in state waiting      ← 一个问题一个答案
```

### 一个只有真机才能抓到的 bug

第一次的结果是 `task="indexing"` 与 `progress=-1%`:文档在**第一个空格**处被截断了。控制台按空格
切分参数,而 `work feed` 只把第一个参数交给了解析器,于是任务名丢了后半段,后面所有字段都被丢弃。
**这看起来和"解析器忽略 progress 与 state"一模一样。**

整个过程宿主测试都是通过的,因为它们把文档当作**一个字符串**传入。只有真机才走了控制台自己的
切分逻辑。现在 `work feed` 会把参数重新拼接——`llm ask` 早先因为同样的原因已经这么做了。

这条教训值得留着:**宿主测试通过只说明逻辑对,不说明设备接收输入的方式对。**

九个宿主测试全部通过(含新增的工作模式测试);固件构建通过;上面的记录来自真机,设备在修复了上一次
会话的重启循环之后运行正常。

## 2026-10-14 —— 第 20 次会话：我造成的重启循环、它的修复,以及现在已验证的部分

**状态：** 设备恢复正常。上一次会话遗留的两项检查,一项通过,另一项未通过,原因已实测。

### 那个重启循环,以及它是我造成的

负责人反馈板子在**不停自动重启**,按什么按钮都没用。控制台显示在音频预热那行之后反复出现 panic:

```text
Guru Meditation Error: Core 0 panic'ed (Stack protection fault).
Stack bounds: 0x3fcaa28c - 0x3fcab280      ← 约 4 KB
```

这个栈边界就是**主任务**的。上一次会话的改动在 `passport_app_start()` 里调用 `qr_reserve()`,
而它跑在主任务上——而**预留缓冲意味着编码一个符号**,那需要约六 KB。于是设备在界面起来之前就
panic 并重启,无限循环,这就是**按什么都没用**的原因。

两条教训,都记在会被读到的地方:

- **栈的需求属于接口,不属于"发现它的那次提交"。** `passport_qr.h` 现在写明编码器约需六 KB 栈,
  并警告小栈调用方会以"看起来像重启循环"的方式崩溃。
- **重启循环就是栈故障从外部看起来的样子。** 之前那个症状——主机报 "a device attached to the
  system is not functioning"——其实是这个循环在反复复位 USB 控制台,不是另一个故障。我当时把它
  读成了硬件问题。

### 修复

预留动作移到**应用工作线程**,并把该线程的栈从 4608 提到 **12288 字节**正是为此;主任务里的调用
被删除。

### 真机验证

```text
启动      无 panic;设备在正常运行
uptime    21,793 ms → 30,309 ms,说明它没有在重启
```

并且上一次会话两项检查中的第一项现在**通过**:在热点处于 **down** 的状态下,`prov status` 已经
报出 `ssid Passport-91E1`,`prov qr` 报出 **40 字节**载荷。那正是"按需推导"修复在起作用——上一次
同一条命令报的是 18 字节,也是促成那次修复的陷阱。

### 仍未验证,附实测数据

`font shot qr dark` 报 `could not allocate 24642 B for the snapshot`。提前预留像素缓冲并没有解决
它,原因现在很清楚:配网屏和它的码缓冲起来之后,**根本不存在 24 KB 的连续块**——可用总量约 31 KB,
但是碎片化的。下一次应改用更窄的快照格式(对这个对象,1 位每像素是 1,541 字节,A8 是 12,321 字节),
而不是 16 位那种。

## 2026-10-14 —— 第 19 次会话：把"一次口语回合"的规则先定下来,在选任何服务商之前

**状态：** 宿主测试通过、构建通过;**没有真机验证**,因为设备的 USB 控制台目前不工作(见下)。
本记录不声称任何内容在硬件上跑过。

### 为什么做这个,而不是做需要设备的东西

写入控制台时报 `A device attached to the system is not functioning`。端口能打开,没有残留进程
占着它,而同一台设备此前只有**物理断电重启**之后才恢复。这不是从这里能修的,所以这一轮做的是语音
里程碑里**不需要射频、不需要服务商、也不需要麦克风**的那一半:**一次口语回合的规则**。

那些规则决定了语音界面**是否让人感觉是坏的**,而且一旦和音频驱动缠在一起,它们是最难测的部分。

### 已构建的内容

`passport_voice` 是一个纯状态机,状态有 idle、listening、transcribing、thinking、speaking、
failed;由按键与各阶段事件驱动,每次返回**一个动作**:开麦克风、转录、问模型、朗读、上报失败、
回到 idle。

有四个决定被**写进代码**而不是留给接线的人:

- **设备朗读时麦克风绝不打开。** 这块板子做不了回声消除,所以播放期间开着的麦克风会录到设备自己
  的声音。状态机在离开 listening 时关闭它,**在朗读之前再关一次**;宿主测试把**每个事件跑过每个
  状态**,并断言麦克风**只在 listening 状态下**可能是打开的。将来有人为了"听打断"而打开它,
  会**挂测试**,而不是造出一台自说自话的设备。
- **朗读期间按键被拒绝,而不是排队。** 半双工设备上的"打断"必须先意味着取消这次朗读,而那个决定
  属于调用方;在播放底下悄悄开一轮,正是设备开始录自己那句话的方式。
- **任何阶段失败都能不经重启恢复**:reset 可以清除,再按一次键也可以。
- **安静的房间不是失败。** 空转录由调用方用 reset 上报,于是"什么都没说"安静地回到 idle,而不是
  显示一个错误。

服务商调用留在状态机之外:它返回一个动作,由调用方执行。

## 2026-10-14 —— 第 16 次会话：QR 编码器,并用一个独立实现验证过

**里程碑：** 编码器已经存在,而且它的符号已被**逐个模块**证明正确。它**还没有画到屏幕上**——那是
下一步,本记录不会声称相反。

### 已构建的内容

`passport_qr` 实现字节模式、纠错等级 L、版本 1 到 4——这台设备需要的全部：最长的载荷是 Wi-Fi
加入字符串,而版本 4 能装 78 字节。`tools/make_qr_fixture.py` 从 Python 的 `qrcode` 包生成测试
夹具,`tests/test_passport_qr.c` 逐个模块比对矩阵,不一致时报出第一个不同的坐标。

已验证：四组载荷 × 八个掩码 = **32 次精确矩阵比对**。它们合起来覆盖了模式与长度字段、填充码字、
Reed-Solomon 运算、定位/分隔/时序/校正图形、之字形布点、掩码,以及格式信息。

### 路上发现的两个我自己的错误

**夹具比编码器先错。** `qrcode` 会选择最紧凑的编码方式,而 "HELLO" 用字母数字模式比字节模式更
紧凑——于是参考符号携带的是**不同的码字**,矩阵不一致的原因与这段代码毫无关系。在两份参考上都
强制字节模式之后就好了。这一点写在生成脚本里:不同口径的夹具会把排查引到错误的文件里。

**测试找到了一个真实的空指针解引用。** `passport_qr_encode(text, NULL)` 最后会通过空指针写入,
因为那道判空只在内部构建函数里。现在检查放在真正写入的地方。

### 有一项性质未经验证,以及原因

**惩罚规则选出的掩码没有可比对的权威实现。** 原计划用 `segno` 对比,它实现的正是规范里的惩罚
规则。但它不能用:按标准顺序从 segno 自己的矩阵里取出码字,会在填充码字之前多出一个零字节——

```text
segno,提取出来   : 40 54 84 54 C4 C4 F0 00 EC 11 ...
规范             : 40 54 84 54 C4 C4 F0 EC 11 EC 11 ...
```

——也就是说 segno 编码的是**另一个符号**,打分的也是另一个矩阵。`qrcode` 的自动选择同样不能作
为权威:它用的是邻域计数的启发式,而不是规范里的惩罚规则。

所以:**符号对每一个掩码都被验证正确**,这意味着无论选哪个掩码,得到的都是合法可扫的码;而掩码
选择本身遵循规范惩罚规则(按本文件的实现),自洽,并且已把 segno 的选择记在夹具旁边,供接手的人
查证。掩码影响的是扫码难易,不是码的内容。

一个值得记下的副作用:按标准顺序读参考矩阵并还原出预期码字,同时也确认了本编码器的遍历顺序——
那从来不是一项单独的测试,它是顺带通过的。

## 2026-10-14 —— 第 14 次会话：设备通过自己的热点完成配置

**里程碑：** 首次配置**不再需要串口线**。设备自己起一个受保护的热点,在上面提供设置页面,并把
收到的设置存下来。

### 已构建的内容

`passport_portal` 是纯 C 的请求逻辑 + 宿主测试：路由选择（**包含 Android、Apple、Windows、
Firefox 用来判断"这个网络是否需要登录页"的那些探测路径**）、
`application/x-www-form-urlencoded` 解码（含 `%XX` 与 `+`）、以及 HTML 转义——最后这项是因为
来自网络的值会出现在页面里。

表单到配置的映射也在那个纯模块里,宿主测试会**拿它和配置 schema 交叉核对**：门户接受的每一个
字段都必须指向 schema 里真实存在的字段。否则一个拼写错误,只有等用户的设置**悄悄没保存**时才会
被发现。

`passport_provision` 是射频与服务器那一侧：APSTA 模式的热点,名称与密码由 MAC 推导（跨重启稳定、
每台设备唯一、显示在屏幕上）、**用 WPA2 密码而不是开放网络**、`esp_http_server` 提供 `/`、
`/save`、`/api/status`、`/api/config`,以及一个把所有探测路径重定向到设置页的兜底处理器。密钥
**永远不会作为输入框的值被渲染**:页面只说明是否已设置,除非你输入新值否则什么都不提交。空字段
一律表示"保持不变",因此一次粗心的保存**不会毁掉一个正在工作的密钥**。

控制台新增 `prov status|start|stop|page [route]|form <k=v>`,上面每一条都是靠它、在没有浏览器的
情况下验证的。

### 两个真机发现

**起热点把 station 踢下线了。** 两个接口共用同一个射频,而热点强行用信道 6,网络在信道 1。现在
热点跟随 station 的信道,关联得以保留——通过对比 `prov start` 前后的 station 地址验证。

**热点的 SSID 字段是固定 32 字节、不预留终止符的数组。** 编译器的 format-truncation 警告抓到了
和 station 路径同一类的 bug;两处现在都显式检查长度并拷贝。

同时加了有上限的自动重连：掉线会重试最多五次,而**你主动要求的断开不会被重试**。

### 真机验证

```text
prov status        先 down,后 up:Passport-91E1、密码由 MAC 推导、192.168.4.1
wifi status        prov start 前后都连接在 192.168.3.75
prov page status   {"wifi":"connected","rssi":-41,...,"largest_block":57344}
prov page /generate_204   解析为重定向路由
prov form pet_name=Whale&volume=55   应用并保存;随后配置读出 volume 55
prov form wifi_password=&pet_name=   "没有可应用的内容";已存密码完好无损
prov stop          ESP_OK
```

### 未验证的部分,以及原因

**从客户端经热点发出的真实 HTTP 请求**。设备自己的客户端到不了 192.168.4.1——"Host is
unreachable"——因为出站流量走的是 station 接口,请求不会环回到热点。这是**路由性质,不是门户
缺陷**;要证明浏览器那条路,得用手机连上 `Passport-XXXX`。**这正是本里程碑交到你手上的用户检查**：
连上那个热点,captive portal 应当自动弹出来。

## 2026-10-14 —— 第 12 次会话：字体接上了、也量了——内置子集不够用

**里程碑：** 显示现在通过应用自己选择的字体现渲染中文，而且固件里带上了**在真机上测量字形覆盖**
的工具。而测量结果说明：LVGL 随附的那个字体**撑不起本产品的对话**。

### 已构建的内容

`passport_fonts` 为对话文本选择 Source Han Sans SC 16，并按仓库字体指南给出的模式挂上 Montserrat 14
作为回退，同时暴露指南自带的那套字形检查。`passport_utf8` 处理码点，更重要的是**按字符边界截断**：
此前回复缓冲是按字节数切的，那会把一个汉字切成两半，留下无效尾巴，而它渲染出来是**什么都没有**。

控制台新增 `font probe`（固定中文样本）、`font check`（**屏幕上真正显示的文本**）、`font shot`
（把会话面板渲染成 ASCII 图）。最后这个要靠两个踩出来的事实：LVGL 的快照是从它自己 24 KB 内存池里
分配的，所以面板图改用**系统堆**的缓冲；面板自身的几种颜色必须从"有墨水"的判定里排除，否则强调条和
圆角都会被当成文字。

界面文本改为中文——这是字体工作终于允许的事。

### 这次测量，以及它纠正了什么

`font probe` 用仓库指南建议的样本**通过了**：只有我刻意放进去的 emoji 缺字形。**那是个陷阱**——
那些样本字正好是 LVGL 自家字体是围绕它们构建的。

`font check` 对模型**真实回答**给出的结论完全不同。一次回复有 22 个码点，其中 **8 个没有真字形**：

```text
text   : 嘿，很高兴见到你！今天有什么我可以帮你的吗？
missing: U+563F U+5174 U+89C1 U+FF01 U+4E48 U+5E2E U+5417 U+FF1F
```

这里面有常用词，而且对一个聊天界面来说更糟的是——**全角的感叹号和问号也缺**。面板的 ASCII 快照
直接显示了后果：那些字符的位置上是**空心的占位方块**。

所以内置子集是给 LVGL 自己测试用的精选样本，不是通用中文字体，会话屏在中文下**还不算诚实**。证明
这一点的工具现在已经是固件的一部分，而修法是指南里的方案 B：用**已经随 LVGL 一起提供的 OFL
Source Han Sans SC** 生成应用自己的子集，字符清单要真实，且**清单与转换命令都要纳入版本控制**。

### 诚实的结论

覆盖基础设施 PASS；对有字形的字符，渲染已由快照确认；**字体资源本身对真实回复 FAIL**——这是一个
被刻意上报的失败，而不是一个"通过"的探测。

## 2026-10-14 —— 第 11 次会话：按一下，屏幕作答

`passport_chat` 是一个 12288 字节栈的工作任务——TLS 握手所需的量，是用"控制台任务在 4096 时
崩溃"这个代价换来的。它的响应缓冲在设备生命周期内只分配一次，而不是每回合分配，因为小堆上

表情、发请求、解出回答、以说话表情呈现。工作任务在碰网络之前就能看出的失败——未配置模型、

### 真机验证

```text

ui get chat/bubble   text: Hi. Press OK.
ui key ok click
ui get chat/bubble   text: Hello there!     ← 模型的回答,就在屏幕上
ui get mood          speaking
```

一次按键产生了一次对模型的 TLS 请求，解出回复并放到屏幕上，而控制台读回的正是人眼所见。

### 我自己控制台里的一个契约 bug，被"需要用到它"暴露出来

`ui names` 为那句回答打印 `obj_3/bubble`，而 `ui get obj_3/bubble` 却拒绝同一个字符串。
列表会为未命名对象合成句柄，而解析器只匹配用户设置的名称，于是控制台打印出了**自己读不了的
路径**——而那个唯一能证明模型确实回复过的字符串，恰好就是这样一条路径。现在解析器两种形式都
接受，并且给会话面板起了名字 `chat`，路径因此是 `chat/bubble`。文档里的契约也连同原因一并
更新，而不只是改规则。

## 2026-10-14 —— 第 10 次会话：解码器，以及一次真实的中文回复

**里程碑：** 响应通路完整了——模型的回答被提取并呈现出来，而且中文可用。

### 已构建的内容

`passport_json` 从服务商响应里解出一个字符串值，纯 C 并带宿主测试。两个性质是刻意的：

转义都处理了，包括 `\uXXXX` 到 UTF-8。基本多文种平面之外的码点变成 `?` 而不是去猜；
emoji 保真不值得一个未经验证的代理对解码器，宿主测试把这个决定钉住了。

`llm ask <text>` 发送一个真实问题并打印回答。它的响应与回答缓冲放在堆上而不是栈上，因为
控制台任务的栈已经要装下一次 TLS 握手。

### 真机验证

```text

llm ask reply in Chinese, one short sentence: who are you
  1859 ms, 响应 518 B
  reply: 我是你的AI助手，可以帮你解答问题和提供帮助。

```

### 一个我差点当成 bug 记下的测量假象

第一次抓中文时显示 `reply: ??????????????`。那其实是我的串口读取没有设置编码——固件没
问题。改读原始字节并按 UTF-8 解码后，文本完全正确。这一点值得写下来：我差点把一个并不
存在的固件缺陷记进日志，是检查了采集侧才拦住的。

一次对话回合在 TLS 活跃下的实用数字是**最大连续空闲块 64 KiB**——裸探测是 68 KiB，减去

往串口控制台里输入非 ASCII 字符并不可靠：有一次中文提示被控制台的行读取器拒绝，另一次

但它意味着中文提示应当通过语音通路验证，而不是假定控制台能行。

## 2026-10-14 —— 第 8 次会话：HTTPS 传输，以及设备帮我抓到的崩溃

```text
assert failed: tcpip_send_msg_wait_sem /IDF/components/lwip/lwip/src/api/tcpip.c:454 (Invalid mbox)
```

## 2026-10-14 —— 第 7 次会话：Wi-Fi station，以及编译器抓出的截断 bug

**里程碑：** 网络层。设备现在能用配置里的凭据找到并加入网络。

### 已构建的内容

新增两个配置字段 `wifi_ssid` 与 `wifi_password`（密码标记为 secret）。由于结构布局变了，

### 编译器抓出了一个真 bug

把 SSID 与密码写进 Wi-Fi 协议栈字段时用 `snprintf`，触发了
`-Werror=format-truncation`：配置允许 95 字符，而协议栈只允许 SSID 31、密码 63。
静默的后果会是**关联到另一个网络**，或者把密码截断后报"密码错误"——而那其实是固件 bug。
现在连接路径会检查两个长度，并按实际上限明确拒绝，不再截断。

### 我自己的一处报告 bug，靠读输出发现

的 blob。现在 dirty 标志的含义与措辞一致——**"生效配置与已存配置不同"**——并且在"没找到
已存配置""版本或大小不符""NVS 打不开"三种情况下都会被置位。已通过观察
`stored=no (unsaved changes)` 在 `config save` 之后变成 `stored=yes` 得到验证。

### 真机验证


## 2026-10-14 —— 第 5 次会话：音频通路，以及实测带来的两个发现

**里程碑：** 麦克风与扬声器通路已进入应用并在真机验证；M1 验收标准中的音频部分完成一半。

### 已构建的内容

`passport_audio_arbiter` 是音频通路的归属状态机，纯逻辑 + 宿主测试：录音与播放不能同时
持有通路、只有当前持有者才能释放、播放持有期间不允许开麦克风。**"播放期间麦克风静音"
这条要求现在就住在这里**——是被强制的代码，而不是日后某个功能可能忘掉的约定。

`passport_audio` 是编解码器侧：16 kHz 16 位单声道、按有界分块收发、在同一份数据上算峰值
保持电平（复用已有宿主测试的 PCM 助手）、一个用于喇叭自检的 1 kHz 单音生成器，以及一条
预热路径。

控制台新增 `audio status`、`audio tone`、`audio loopback`、`audio mute-check`。

### 两个发现，都来自实测而不是假设

**编解码器最先吐出来的样本不是音频。** 开机后的第一次录音报告 rms 31,106、peak 32,768——
在一个安静的房间里读出了削顶的满幅"输入"。加上每次打开时的 100 ms 守卫后降到
rms 7,627 / peak 9,087，仍是稳态（rms ~100 / peak ~237）的 76 倍。现在应用在启动时用
500 ms 丢弃做一次预热，第一次面向用户的录音读到 rms 148 / peak 286。没有这一步，开机后
每一次语音回合都会看起来像有人在喊——这很可能是日后"转录听不到有用内容"这类 bug 的成因。

**静音规则可以在设备上被证明，而不只在测试里。** `audio mute-check` 先以播放身份占用通路，
再尝试录音，并报告是否被拒绝。宿主测试已穷尽覆盖同一条规则；这是它在真机上的对应物。

### 真机验证

```text
                     播放完成(归属恢复 free)
```

### 产品负责人对已刷固件的手动测试

负责人实际操作了刷入的基线应用，反馈"都没啥问题"，只有一处观察：**深睡唤醒时应用重启了**。

这是文档规定的契约，不是缺陷。`esp_deep_sleep_start()` 不会返回；芯片复位、应用重新启动。
仓库自己的参考笔记记录过本板上的同一行为，包括：深睡期间 USB-Serial/JTAG 控制台会消失、
唤醒后恢复，并且启动日志会打印唤醒原因——这正是文档给出的"在真机上确认唤醒源"的方法。

两条值得留住的推论：

- **浅睡不一样。** 浅睡原地恢复、不重启。需要无缝恢复的设计必须走浅睡或常连配置，而常连
  正是负责人已经选定的默认（`Q-8`）。因此出厂默认在闲置时不会重启。
- **深睡正是控制台第一次刷写时消失的原因**，也是为什么在主机连着 USB 口时，基线 demo 的
  Low Power 页不适合当作调试工具。

未验证：这次观察没有被仪器记录。当时没有抓取唤醒原因那一行日志，所以唤醒源目前依据的是
文档而不是来自本机的日志。日后抓一次唤醒原因行即可补上这个缺口。

### 串口控制台已在真机验证

控制台已刷入并在 `COM47` 上实操。检查与控制都可用，而且这一轮在控制台自身里找出了一个真缺陷。

可用部分：`ver` 报告构建 `4d05296`；`ui screen` 报告 `menu 240x320 children=39`；
`ui names` 把每个控件按路径连同屏幕文字打印出来，包括由可见标签推导出的名字
（`display`、`button`、`audio`、`battery`、`wi-fi`、`ble`、`low-power`）；
`ui key down click` 再 `ui key ok click` 进入页面；`ui tree 1` dump 出新屏幕；
`ui key ok long` 返回菜单。闭环成立——主机既能驱动设备，也能读回屏幕上画了什么。

发现并修复的缺陷：在这个 LVGL 版本里，`lv_obj_get_name_resolved()` 对**未命名的根屏幕**会
以 load access fault 崩溃。它之前看起来能用，只是因为菜单屏幕带了用户设置的名字。现在
控制台直接读 `lv_obj_get_name()`，对未命名控件合成标签，并用自己实现的遍历来解析路径，
不再走 LVGL 的名字查找。由此产生一条需要明确写下的约束：**只有带用户设置名字的控件可被
寻址**；未命名控件仍会出现在控件树里供查看。

同一轮还发现：基线 demo 的菜单由**按键事件**驱动，而不是控件点击，所以在那里 `ui tap`
进不去页面——卡片没有注册点击处理。`ui tap` 对会注册处理的界面依然正确，M1 应用就会注册。

控制台在线期间在菜单屏幕上取得的测量值：可用堆 142,600 B、历史最低 138,544 B、
**最大连续空闲块 112 KiB**；LVGL 内存池 24 KB 中剩余 4,008 B、历史峰值 18,452 B、碎片率 9%；
电量 97%；按键松开电压 2,964 mV。那个内存池数字是第一个具体迹象，说明基线 demo 已经把
24 KB 的池用掉了大半。

### 宠物设计

首版设计已存在，由一个新增的生成脚本产出。

- 角色是一只朝右的 32 × 32 逻辑网格鲸鱼，以 2× 写为 64 × 64 精灵图，使用十一种
  不透明颜色，锚定在品牌蓝色 `#4D6BFE` 上。
- 十一帧覆盖待机（两帧呼吸起伏）、眨眼、好奇、聆听、思考、工作、说话、开心、
  睡觉和苦恼。
- 每帧为 12,288 B（RGB565A8）；十一帧共占用 132 KiB flash，相对于 8 MB 无关紧要。
  各帧共享相同的边界，因此动画只替换一个图像源，绝不改变常驻对象数量。
- 生成脚本仅使用 Python 标准库，因此可在任何环境运行，并产出字节一致的输出。
- 该设计正在等待产品负责人验收确认，且重绘成本很低：几何常量与调色板就是全部的
  可改面。

### 研究发现

**配套的智能体侧项目（已报告，未针对运行中的宿主验证）。**
该配套插件仓库是 DeepSeek Harness 插件包，而不是独立应用。它为工作状态和增量
通知帧发布只读的本地 JSON 端点，以及一个接受待确认问题答案的端点。这项工作得出了
两条约束，二者都很重要：

- 它自己的文档把将 harness Web 服务器暴露到网络视为等同于远程代码执行，且其
  服务器只绑定回环地址。
- 问题投递端点在该仓库内被描述为一条不可靠触发的不完整路径，因此必须先验证问题
  捕获，绝不能假设其可用。

后果：工作模式集成经由一个专门构建的桥接服务进行，它是唯一面向局域网的面。

**语音架构。** 两项已发布的事实压缩了设计空间。在这款芯片上，Wi-Fi station 加
一条 TLS 连接在默认配置下的可用堆约为 210 KB；而乐鑫音频前端——包括每一种回声
消除模式，这些模式还额外需要 PSRAM——不支持此目标。唯一真正有用的正面发现是，
多家语音合成提供方都提供原始线性 PCM 输出，从而把音频解码器从固件中完全移除。

**配网与 Web 后台。** ESP-IDF 配网管理器的软接入点传输使用 protobuf，且需要厂商
手机 SDK，因此无法满足"无需单独应用"；配网服务器和配网门户页必须直接编写。所固定
的 LVGL 版本已经包含一个二维码控件，它以每像素一位存储其画布，因此该代码无需新的
依赖。只有当需要空中升级时，分区表变更才成为必要。

### 决策

| ID | 决策 | 原因 |
| --- | --- | --- |
| D-1 | 新的 fork readme 是一对仓库根目录的 readme；上游项目概览文档保持不动 | fork 工作流为 fork 所有者保留根 readme，禁止就地编辑上游概览，而重命名它会在每次上游同步时产生冲突。创建根 readme 还能获得 GitHub 的显示优先级，因此它取代旧 readme 成为可见的项目页面 |
| D-2 | Fork 私有的设计文档放在 `docs/assets/` 下 | 那是文档规定的 fork 自有位置，用于架构笔记、产品设计和补充文档 |
| D-3 | 提供方编排默认位于配套桥接服务中；设备直连仅作为可配置的回退方案 | 消除最大的 RAM 风险，让密钥远离可能丢失的设备，使提供方无需固件发布即可配置，并统一音频格式 |
| D-4 | 工作模式只经由桥接服务访问智能体主机，绝不直接访问 | 出于有文档记载的安全原因，智能体主机的本地服务器仅绑定回环地址 |
| D-5 | 半双工按键说话，播放期间麦克风静音 | 在这款硬件上有两个彼此独立的原因导致回声消除（AEC）不可用；若不静音，设备会转录自己的扬声器 |
| D-6 | 端到端使用原始 PCM；设备上不设音频编解码器 | 实测解码器开销相对于 210 KB 堆而言很大，而提供方可免费提供 PCM |
| D-7 | 像素风美术由驻留 flash 的图像描述符渲染，而不是用大量 LVGL 对象或逐帧画布 | 对象和画布分配来自较小的 LVGL 内存池；而 flash 实际上不受限 |
| D-8 | 配网服务器直接编写，而不是使用配网管理器的软接入点传输 | 管理器的传输需要厂商手机应用，且不提供门户页 |
| D-9 | 空中升级推迟到产品负责人回答 `Q-6` 之后 | 它会强制改变分区表并制定回滚策略，这不是可以悄悄做出的决策 |
| D-10 | 唤醒词激活被推迟，而不是宣布其不可行 | 小型无 PSRAM 的唤醒词模型确实支持这款芯片；推迟的原因是成本与空闲功耗，而非能力 |
| D-11 | 设计文档即这一套：需求、架构、语音后端、路线图，以及本日志 | 每个问题只有一个权威归属，不重复事实来源 |
| D-12 | 架构文档中的每一项定量声明都标注为实测值、已发布数字或估算值 | 最初的草稿中有两处估算被写成了事实；开发板上有足够的实测经验可以避免这一点 |
