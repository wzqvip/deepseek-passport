## 2026-10-14 —— 第 11 次会话：按一下，屏幕作答

**里程碑：** 按 OK 现在能与模型对话，而且回答可以从串口控制台读回。

### 已构建的内容

`passport_chat` 是一个 12288 字节栈的工作任务——TLS 握手所需的量，是用"控制台任务在 4096 时
崩溃"这个代价换来的。它的响应缓冲在设备生命周期内只分配一次，而不是每回合分配，因为小堆上
的反复分配正是碎片化的来源。按 OK 只是把提示词入队并立即返回；工作任务取 LVGL 锁、显示思考
表情、发请求、解出回答、以说话表情呈现。工作任务在碰网络之前就能看出的失败——未配置模型、
未关联网络——直接显示在屏幕上，而不是躲在十五秒的 DNS 超时后面。

### 真机验证

```text
ui names             chat/bubble   label   "Hi. Press OK."
ui get chat/bubble   text: Hi. Press OK.
ui key ok click
ui get chat/bubble   text: Hello there!     ← 模型的回答,就在屏幕上
ui get mood          speaking
```

一次按键产生了一次对模型的 TLS 请求，解出回复并放到屏幕上，而控制台读回的正是人眼所见。

### 我自己控制台里的一个契约 bug，被"需要用到它"暴露出来

`ui names` 为那句回答打印 `obj_3/bubble`，而 `ui get obj_3/bubble` 却拒绝同一个字符串。
列表会为未命名对象合成句柄，而解析器只匹配用户设置的名称，于是控制台打印出了**自己读不了的
路径**——而那个唯一能证明模型确实回复过的字符串，恰好就是这样一条路径。现在解析器两种形式都
接受，并且给会话面板起了名字 `chat`，路径因此是 `chat/bubble`。文档里的契约也连同原因一并
更新，而不只是改规则。

### 本里程碑暴露出的前置条件

显示字体仍然没有中日韩字形，所以中文回答会渲染成空白方块，按钮目前因此用英文提问。这一点被
记为**中文优先产品的前置条件**而不是细节：回复里有 UTF-8、构建成功，都**不能证明字形存在**，
仓库的字体检查清单就是这么写的。在中日韩像素字体落地之前，会话屏只有在英文下才是诚实的
——这是产品上的真实缺口，不是管线上的。

## 2026-10-14 —— 第 10 次会话：解码器，以及一次真实的中文回复

**里程碑：** 响应通路完整了——模型的回答被提取并呈现出来，而且中文可用。

### 已构建的内容

`passport_json` 从服务商响应里解出一个字符串值，纯 C 并带宿主测试。两个性质是刻意的：

- 键**连同两侧引号一起匹配**，所以查找 `"content"` 不会命中 `"reasoning_content"`
  内部。这一点很要紧：DeepSeek 的思考模式会在回答旁边返回模型的推理过程，而一个天真的
  子串搜索会把推理塞进宠物的对话气泡。
- 解码有界，并且**截断时连同完整长度一起上报**，调用方因此知道自己丢了多少。这是把仓库
  自己记录过的教训——固定 4096 字节文档撞上 6971 字节响应——变成 API，而不是一条注释。

转义都处理了，包括 `\uXXXX` 到 UTF-8。基本多文种平面之外的码点变成 `?` 而不是去猜；
emoji 保真不值得一个未经验证的代理对解码器，宿主测试把这个决定钉住了。

`llm ask <text>` 发送一个真实问题并打印回答。它的响应与回答缓冲放在堆上而不是栈上，因为
控制台任务的栈已经要装下一次 TLS 握手。

### 真机验证

```text
llm ask say "hi" in JSON
  1740 ms, 响应 492 B, 会话活跃时最大连续空闲块: 64 KiB
  reply: 一段围栏 JSON                  ← 内嵌的引号与换行都完好保留

llm ask reply in Chinese, one short sentence: who are you
  1859 ms, 响应 518 B
  reply: 我是你的AI助手，可以帮你解答问题和提供帮助。
  回复行中的中日韩字符数: 19
```

### 一个我差点当成 bug 记下的测量假象

第一次抓中文时显示 `reply: ??????????????`。那其实是我的串口读取没有设置编码——固件没
问题。改读原始字节并按 UTF-8 解码后，文本完全正确。这一点值得写下来：我差点把一个并不
存在的固件缺陷记进日志，是检查了采集侧才拦住的。

一次对话回合在 TLS 活跃下的实用数字是**最大连续空闲块 64 KiB**——裸探测是 68 KiB，减去
ask 的缓冲——这就是音频流水线必须与之共处的预算。

### 已知限制

往串口控制台里输入非 ASCII 字符并不可靠：有一次中文提示被控制台的行读取器拒绝，另一次
被接受。中文输入的产品通路是语音而不是手打控制台输入，所以这是工具限制而非产品限制——
但它意味着中文提示应当通过语音通路验证，而不是假定控制台能行。

## 2026-10-14 —— 第 9 次会话：设备与 DeepSeek 通了，那个 TLS 数字也到手了

**里程碑：** 服务商通路端到端打通，架构文档一直等的那个测量值拿到了。

### 结果

关联上网络并执行 `llm probe` 之后：

```text
llm probe: HTTP 200, 452 bytes, 1730 ms
  会话活跃时: 可用堆 80376 B, 最大连续空闲块 69632 B(68 KiB)
  body: {"id":"...","object":"chat.completion",...,"model":"deepseek-flash",
         "choices":[{"index":0,"message":{"role":"assistant","content":"p"},
         "finish_reason":"length"}],...}
```

**真的返回了一次补全。** 这一个结果同时证明了：DNS 解析、带证书包的 TLS 握手、HTTP POST、
Bearer 凭据、服务商响应，以及带上限的读取通路——含握手共 1,730 ms，这也是时延预算的第一个
真实数字。

### 一直缺失的那个数字

| 状态 | 可用堆 | 最大连续空闲块 |
| --- | --- | --- |
| 空闲、未开射频 | 154,624 B | 112 KiB |
| 已关联 Wi-Fi、无 TLS | 163,580 B | 112 KiB |
| **TLS 会话活跃** | **80,376 B** | **68 KiB** |

一旦存在 TLS 会话，**最大连续空闲块从 112 KiB 掉到 68 KiB**。这正是本项目一直称为"真正
约束"的那个指标，如今是实测而非估算。它仍明显高于分块 PCM 流水线所需，所以直连模式依然可行
——但余量是 **68 KiB 而不是 112 KiB**，今后每一个缓冲区都要拿这个数字来衡量。

### 又一个只有真机才能暴露的崩溃

`llm probe` 第一次以 `Guru Meditation Error: Stack protection fault` 死在 `console_repl`
任务里。控制台任务的栈只有 4096 字节，装不下一次 mbedTLS 握手；现在改为 10240 字节，并把
原因写在设置旁边，免得下一个人又把它调小。这是本里程碑第二个从源码看不出来的缺陷。

### 凭据

Wi-Fi 密码与 API Key 由负责人提供，**只写入设备的 NVS**。没有提交、没有写进文档、没有被
记录到日志；控制台只把它们渲染为"已设置/为空"，并且我把抓到的设备输出对这两个字符串都做了
检查——都没有出现。密钥按负责人的选择经过了聊天记录，因此**轮换与否由负责人决定，代价只是
一条控制台命令**。

## 2026-10-14 —— 第 8 次会话：HTTPS 传输，以及设备帮我抓到的崩溃

**里程碑：** 服务商通路中的传输半程。设备现在能发出 HTTPS 请求并报告返回内容，包括会话
活跃期间的堆内存。

### 已构建的内容

`passport_http` 用 `esp_http_client` 发一次请求，把响应读进调用方提供的缓冲并设硬上限，
**截断时如实上报而不是掩盖**——仓库里已有一条关于"固定 4096 字节文档遇到 6971 字节响应"
的记录。它在 **TLS 会话已建立时**取可用堆与最大连续空闲块的读数，因为那正是直连模式预算所
依赖的数字；在握手之前或之后测量，都会错过它本该捕捉的开销。

证书包已启用；TLS 记录缓冲从默认 16 KB 降到 4 KB，好让测量反映**真正计划使用的配置**而
不是默认值。控制台命令：`net probe <url>` 与 `llm probe`。后者用配置构造一个最小的对话补全
请求；当端点或模型未设置时，它会拒绝并给出要执行的命令。

### 真机上跑出来的崩溃

第一次在硬件上执行 `net probe` 时，lwIP 断言失败：

```text
assert failed: tcpip_send_msg_wait_sem /IDF/components/lwip/lwip/src/api/tcpip.c:454 (Invalid mbox)
```

原因在我：创建套接字需要网络协议栈，而此前只有 Wi-Fi 命令初始化过它。现在
`passport_net_init()` 负责 `esp_netif` 与默认事件循环，Wi-Fi 模块在其之上构建，HTTP 客户端
在碰套接字之前先调用它。**库函数不应假设某个全局初始化已经跑过。**

修复后验证：`net probe https://api.deepseek.com/` 因 `getaddrinfo()` 干净失败而返回
`ESP_ERR_HTTP_CONNECT`，设备继续运行，后续命令正常响应。

### 我自己的一个工具用法错误

有一次刷写"失败"了，却在打印成功行。原因是把 `Select-Object -First N` 用在了原生命令的输出
上：它会**短路整条管道并可能终止上游进程**，于是我读到的退出码其实来自我自己的过滤器，而
不是工具。应当先把退出码读进变量再过滤。那次刷写其实是成功的。

### 被一个输入卡住

要验证 TLS 握手、401 响应通路，以及"活跃 TLS 会话下的最大连续空闲块"这个数字，设备必须先
关联上一个网络。那需要负责人的 SSID 与密码：不是我该编造的，而且扫描列表也不该被提交。
到这一步为止的工作都已完成并验证；关联与真实服务商往返，是拿到凭据后的下一步。

## 2026-10-14 —— 第 7 次会话：Wi-Fi station，以及编译器抓出的截断 bug

**里程碑：** 网络层。设备现在能用配置里的凭据找到并加入网络。

### 已构建的内容

新增两个配置字段 `wifi_ssid` 与 `wifi_password`（密码标记为 secret）。由于结构布局变了，
schema 版本升到 2——这也让版本守卫得到了一次真实演练（见下）。

`passport_wifi` 负责把 station 拉起来：netif、默认事件循环、station 接口、事件处理，
然后扫描与连接。凭据只来自配置存储，绝不来自源码。两个操作都是阻塞的，因此属于任务上下文，
不能放在按键回调或 LVGL 定时器里。

控制台命令：`wifi status`、`wifi scan`、`wifi connect [ms]`、`wifi disconnect`。

### 编译器抓出了一个真 bug

把 SSID 与密码写进 Wi-Fi 协议栈字段时用 `snprintf`，触发了
`-Werror=format-truncation`：配置允许 95 字符，而协议栈只允许 SSID 31、密码 63。
静默的后果会是**关联到另一个网络**，或者把密码截断后报"密码错误"——而那其实是固件 bug。
现在连接路径会检查两个长度，并按实际上限明确拒绝，不再截断。

### 我自己的一处报告 bug，靠读输出发现

版本不匹配之后控制台打印了 `stored=yes`，这是不实的：当时生效的是默认值，而存储里是旧版本
的 blob。现在 dirty 标志的含义与措辞一致——**"生效配置与已存配置不同"**——并且在"没找到
已存配置""版本或大小不符""NVS 打不开"三种情况下都会被置位。已通过观察
`stored=no (unsaved changes)` 在 `config save` 之后变成 `stored=yes` 得到验证。

### 真机验证

```text
config list   版本升级后:v1 blob(1260 B)与 v2 结构(1452 B)不符被拒绝,装入默认值,
              报告 stored=no;config save 之后报告 stored=yes
wifi status   idle、address (none)、ssid (not configured)、password (empty)
wifi scan     17 个接入点,RSSI 从 -30 到 -85 dBm,信道 1 到 11
wifi connect  未配置 SSID:立即拒绝,并给出要执行的三个命令
wifi connect  不存在的 SSID:经断开事件返回 ESP_FAIL,状态变为 failed
```

扫描结果**刻意不在此复现**：它包含周边邻居的网络名称，那不是本项目应当记录的数据。设备自身
的 MAC 地址出于同样原因也不记录。

## 2026-10-14 —— 第 6 次会话：配置存储

**里程碑：** 语音、工作模式、Web 后台三个里程碑都依赖的设置与凭据层。

### 已构建的内容

`passport_config` 是配置结构与访问器，纯 C，并带宿主测试：**一张字段表**同时驱动今天
的控制台和日后的 Web 后台；默认值可重复应用；数值按边界钳制；过长字符串被拒绝而不是
截断；**标记为 secret 的字段永远不会被渲染**——`passport_cfg_format()` 对它只返回
"(set)" 或 "(empty)"，因此凭据不可能从日志、转录文本或控制台列表里泄露出去。

`passport_config_store` 把整个结构作为一个 NVS blob、一个键持久化，并把"大小或版本不符"
当作"改用默认值"，而不是把旧字节重新解释成新字段。NVS 初始化失败**绝不触发擦除**：设备
如实报告，然后用默认值继续运行。

`main.c` 的启动流程现在包含 NVS 与配置，并且**存下来的偏好真正生效**：亮度作用于背光，
音量在编解码器打开时被采用，替换了原先写死的常量。

控制台命令：`config list`、`config get`、`config set`、`config save`、`config reset`。

### 真机验证

```text
config list           默认值;secret 显示为 (empty) [secret];
                      llm_base_url https://api.deepseek.com
config set llm_api_key sk-hidden-42    ->  = (set) [secret]
config set llm_model deepseek-chat
config set volume 35
config save           ESP_OK
reboot
config list           llm_api_key (set)、llm_model deepseek-chat、volume 35
config get llm_api_key ->  (set)   (密钥永不打印)
```

跨重启持久化成立，且存下的凭据永不被渲染。密钥规则是**断言出来的，不是靠眼看**：滤掉
控制台对我所输入命令的回显后，`sk-hidden-42` 在设备自身的输出里一次都没有出现。

## 2026-10-14 —— 第 5 次会话：音频通路，以及实测带来的两个发现

**里程碑：** 麦克风与扬声器通路已进入应用并在真机验证；M1 验收标准中的音频部分完成一半。

### 已构建的内容

`passport_audio_arbiter` 是音频通路的归属状态机，纯逻辑 + 宿主测试：录音与播放不能同时
持有通路、只有当前持有者才能释放、播放持有期间不允许开麦克风。**"播放期间麦克风静音"
这条要求现在就住在这里**——是被强制的代码，而不是日后某个功能可能忘掉的约定。

`passport_audio` 是编解码器侧：16 kHz 16 位单声道、按有界分块收发、在同一份数据上算峰值
保持电平（复用已有宿主测试的 PCM 助手）、一个用于喇叭自检的 1 kHz 单音生成器，以及一条
预热路径。

控制台新增 `audio status`、`audio tone`、`audio loopback`、`audio mute-check`。

### 两个发现，都来自实测而不是假设

**编解码器最先吐出来的样本不是音频。** 开机后的第一次录音报告 rms 31,106、peak 32,768——
在一个安静的房间里读出了削顶的满幅"输入"。加上每次打开时的 100 ms 守卫后降到
rms 7,627 / peak 9,087，仍是稳态（rms ~100 / peak ~237）的 76 倍。现在应用在启动时用
500 ms 丢弃做一次预热，第一次面向用户的录音读到 rms 148 / peak 286。没有这一步，开机后
每一次语音回合都会看起来像有人在喊——这很可能是日后"转录听不到有用内容"这类 bug 的成因。

**静音规则可以在设备上被证明，而不只在测试里。** `audio mute-check` 先以播放身份占用通路，
再尝试录音，并报告是否被拒绝。宿主测试已穷尽覆盖同一条规则；这是它在真机上的对应物。

### 真机验证

```text
audio status         归属 free,麦克风允许
audio loopback 1000  采集 16000 样本 rms=148 peak=286
                     播放完成(归属恢复 free)
audio mute-check     播放持有通路期间录音被拒绝:是
audio tone 300       ESP_OK
app                  free=217,844 B min=185,144 B largest=114,688 B
                     lvgl free=14,084 biggest=13,996 frag=1% max_used=9,264
```

## 2026-10-14 —— 第 4 次会话：应用本体取代 demo 菜单

**里程碑：** 应用本体已开工，第一屏是宠物主页面。

### 已完成的工作

上游的硬件测试菜单已从构建中移除。`main/main.c` 现在是 Passport 的入口：BSP 初始化、
上一次会话留下的深睡按键守卫交接、一个由消费者驱动应用的输入队列、串口控制台，以及一次
启动应用的调用。

第一屏是为这个产品设计的，而不是继承来的：顶部状态条（电量在右上角）、一条强调色分隔线、
带强调色边条的对话面板、宠物精灵图、一行标明当前表情的文字、一条地平线，以及底部提示。
demo 的卡片、云、草地和 `ui_pixel` 外壳是**删除**，不是改色。

宠物（`passport_pet.c`）是一个由 90 ms LVGL 定时器驱动的精灵控件：待机时两帧呼吸起伏并
偶尔眨眼，工作时抬起尾巴，说话时喷水，开心与苦恼有轻微的纵向反应。动画只替换同一个控件的
图像源，因此常驻对象数量从不变化。每种情绪都能用 `UP`/`DOWN` 走到——这正是主机通过控制台
逐一核对整套素材的方式。

电量读取放在应用的工作线程里，而不是 LVGL 定时器里：电量计挂在 I2C 上，在渲染任务里做
阻塞 I/O 正是硬件指南明确警告的做法。工作线程更新标签时持 `bsp_lvgl_lock()`。

### 真机验证

启动日志：找到两个 I2C 器件、显示屏与 LVGL 就绪、应用已启动、控制台就绪，就绪行报告
Display=1 Button=1 Audio=1 Battery=1 App=1。素材行报告 11 帧 64x64、首帧 12,288 B、
共 135,168 B flash——与预测的 RGB565A8 开销一致，说明精灵图确实在镜像里，而不只是被编译过。

从控制台读回的屏幕内容，正是一一对应在起作用：

```text

title               label    "PASSPORT"
battery             label    "97%"
obj_3/bubble        label    "Hi. Press OK."
pet                 widget
mood                label    "idle"
hint                label    "OK: react    hold OK: standby"
```

用注入按键驱动：两次 `ui key down click` 把 `mood` 从 "idle" 走到 "curious" 再到
"listening"，`ui key ok click` 得到 "happy"，每次都通过 `ui get mood` 读回确认。

### 产品负责人对已刷固件的手动测试

负责人实际操作了刷入的基线应用，反馈"都没啥问题"，只有一处观察：**深睡唤醒时应用重启了**。

这是文档规定的契约，不是缺陷。`esp_deep_sleep_start()` 不会返回；芯片复位、应用重新启动。
仓库自己的参考笔记记录过本板上的同一行为，包括：深睡期间 USB-Serial/JTAG 控制台会消失、

两条值得留住的推论：

- **浅睡不一样。** 浅睡原地恢复、不重启。需要无缝恢复的设计必须走浅睡或常连配置，而常连
  正是负责人已经选定的默认（`Q-8`）。因此出厂默认在闲置时不会重启。
- **深睡正是控制台第一次刷写时消失的原因**，也是为什么在主机连着 USB 口时，基线 demo 的
  Low Power 页不适合当作调试工具。

未验证：这次观察没有被仪器记录。当时没有抓取唤醒原因那一行日志，所以唤醒源目前依据的是
文档而不是来自本机的日志。日后抓一次唤醒原因行即可补上这个缺口。

### 串口控制台已在真机验证

控制台已刷入并在 `COM47` 上实操。检查与控制都可用，而且这一轮在控制台自身里找出了一个真缺陷。

可用部分：`ver` 报告构建 `4d05296`；`ui screen` 报告 `menu 240x320 children=39`；
`ui names` 把每个控件按路径连同屏幕文字打印出来，包括由可见标签推导出的名字
（`display`、`button`、`audio`、`battery`、`wi-fi`、`ble`、`low-power`）；
`ui key down click` 再 `ui key ok click` 进入页面；`ui tree 1` dump 出新屏幕；
`ui key ok long` 返回菜单。闭环成立——主机既能驱动设备，也能读回屏幕上画了什么。

发现并修复的缺陷：在这个 LVGL 版本里，`lv_obj_get_name_resolved()` 对**未命名的根屏幕**会
以 load access fault 崩溃。它之前看起来能用，只是因为菜单屏幕带了用户设置的名字。现在
控制台直接读 `lv_obj_get_name()`，对未命名控件合成标签，并用自己实现的遍历来解析路径，
不再走 LVGL 的名字查找。由此产生一条需要明确写下的约束：**只有带用户设置名字的控件可被
寻址**；未命名控件仍会出现在控件树里供查看。

同一轮还发现：基线 demo 的菜单由**按键事件**驱动，而不是控件点击，所以在那里 `ui tap`
进不去页面——卡片没有注册点击处理。`ui tap` 对会注册处理的界面依然正确，M1 应用就会注册。

控制台在线期间在菜单屏幕上取得的测量值：可用堆 142,600 B、历史最低 138,544 B、
**最大连续空闲块 112 KiB**；LVGL 内存池 24 KB 中剩余 4,008 B、历史峰值 18,452 B、碎片率 9%；
电量 97%；按键松开电压 2,964 mV。那个内存池数字是第一个具体迹象，说明基线 demo 已经把
24 KB 的池用掉了大半。

### 研究发现

**配套的智能体侧项目（已报告，未针对运行中的宿主验证）。**
该配套插件仓库是 DeepSeek Harness 插件包，而不是独立应用。它为工作状态和增量
通知帧发布只读的本地 JSON 端点，以及一个接受待确认问题答案的端点。这项工作得出了
两条约束，二者都很重要：

- 它自己的文档把将 harness Web 服务器暴露到网络视为等同于远程代码执行，且其
  服务器只绑定回环地址。
- 问题投递端点在该仓库内被描述为一条不可靠触发的不完整路径，因此必须先验证问题
  捕获，绝不能假设其可用。

后果：工作模式集成经由一个专门构建的桥接服务进行，它是唯一面向局域网的面。

**语音架构。** 两项已发布的事实压缩了设计空间。在这款芯片上，Wi-Fi station 加
一条 TLS 连接在默认配置下的可用堆约为 210 KB；而乐鑫音频前端——包括每一种回声
消除模式，这些模式还额外需要 PSRAM——不支持此目标。唯一真正有用的正面发现是，
多家语音合成提供方都提供原始线性 PCM 输出，从而把音频解码器从固件中完全移除。

**配网与 Web 后台。** ESP-IDF 配网管理器的软接入点传输使用 protobuf，且需要厂商
手机 SDK，因此无法满足"无需单独应用"；配网服务器和配网门户页必须直接编写。所固定
的 LVGL 版本已经包含一个二维码控件，它以每像素一位存储其画布，因此该代码无需新的
依赖。只有当需要空中升级时，分区表变更才成为必要。

### 决策

| ID | 决策 | 原因 |
| --- | --- | --- |
| D-1 | 新的 fork readme 是一对仓库根目录的 readme；上游项目概览文档保持不动 | fork 工作流为 fork 所有者保留根 readme，禁止就地编辑上游概览，而重命名它会在每次上游同步时产生冲突。创建根 readme 还能获得 GitHub 的显示优先级，因此它取代旧 readme 成为可见的项目页面 |
| D-2 | Fork 私有的设计文档放在 `docs/assets/` 下 | 那是文档规定的 fork 自有位置，用于架构笔记、产品设计和补充文档 |
| D-3 | 提供方编排默认位于配套桥接服务中；设备直连仅作为可配置的回退方案 | 消除最大的 RAM 风险，让密钥远离可能丢失的设备，使提供方无需固件发布即可配置，并统一音频格式 |
| D-4 | 工作模式只经由桥接服务访问智能体主机，绝不直接访问 | 出于有文档记载的安全原因，智能体主机的本地服务器仅绑定回环地址 |
| D-5 | 半双工按键说话，播放期间麦克风静音 | 在这款硬件上有两个彼此独立的原因导致回声消除（AEC）不可用；若不静音，设备会转录自己的扬声器 |
| D-6 | 端到端使用原始 PCM；设备上不设音频编解码器 | 实测解码器开销相对于 210 KB 堆而言很大，而提供方可免费提供 PCM |
| D-7 | 像素风美术由驻留 flash 的图像描述符渲染，而不是用大量 LVGL 对象或逐帧画布 | 对象和画布分配来自较小的 LVGL 内存池；而 flash 实际上不受限 |
| D-8 | 配网服务器直接编写，而不是使用配网管理器的软接入点传输 | 管理器的传输需要厂商手机应用，且不提供门户页 |
| D-9 | 空中升级推迟到产品负责人回答 `Q-6` 之后 | 它会强制改变分区表并制定回滚策略，这不是可以悄悄做出的决策 |
| D-10 | 唤醒词激活被推迟，而不是宣布其不可行 | 小型无 PSRAM 的唤醒词模型确实支持这款芯片；推迟的原因是成本与空闲功耗，而非能力 |
| D-11 | 设计文档即这一套：需求、架构、语音后端、路线图，以及本日志 | 每个问题只有一个权威归属，不重复事实来源 |
| D-12 | 架构文档中的每一项定量声明都标注为实测值、已发布数字或估算值 | 最初的草稿中有两处估算被写成了事实；开发板上有足够的实测经验可以避免这一点 |
