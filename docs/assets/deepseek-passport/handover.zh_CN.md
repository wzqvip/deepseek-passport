# 交付说明

这台设备是什么、怎么烧、怎么用——以及最重要的那一部分:**哪些验证过了,哪些没有。**

下面每一条都是**在这块板子上量出来的**。凡是属于"人的检查"而不是机器的检查,它会直接说出来,而不是
被四舍五入成"已完成"。

## 1. 它是什么

一台装在口袋里的 DeepSeek 随身宠物,跑在 ESP32-C3 上。主页是一只**会呼吸、会眨眼**的像素宠物。
**按住一个键、说话、松手**:语音被流式送到局域网上的配套桥接服务,转写、送给 DeepSeek,回答回到屏幕上
并从扬声器里说出来。第二块屏幕镜像桌面的工作会话——任务、进度、一个带选项的问题——用同样三个按键回答。
它能通过热点自助配网(二维码 + Web 后台),也懂得睡觉。

界面是**这个应用自己的**:上游 demo 的菜单、屏幕与视觉外壳是被**删除**的,不是改名。`main/` 与
`tests/` 下再没有任何东西提到 `demo`。

## 2. 烧写

需要激活 ESP-IDF 5.5.3。

```bash
idf.py -p <端口> flash monitor      # 从源码构建并烧写
```

或者烧写**验证过的合并镜像**——它包含引导程序、分区表与应用,一条命令即可写入空白板子:

```bash
esptool.py --chip esp32c3 write_flash 0x0 FoloToy-AI-Passport-full.bin
```

仓库的 `tools/validate.sh --firmware` 会在 `build/` 下生成那个文件。它**不入库**:它是构建产物,不是源码。

**绝不要做全片擦除。** Wi-Fi 凭据与 API Key 存在 NVS 里,全片擦除会毁掉它们;分段方式的
`idf.py flash` 不会。

## 3. 怎么用

主页上:

| 手势 | 作用 |
| --- | --- |
| **按住 OK、说话、松手** | 一次语音回合:录音 → 转写 → 问 DeepSeek → 回答上屏并朗读 |
| 长按 DOWN | 工作模式 |
| 长按 UP | 配网屏:入网二维码、热点名与密码、访问地址 |
| 双击 UP | 待机:深睡,按任意键唤醒 |

工作屏上:UP/DOWN 移动选择,OK 确认,长按 OK 返回主页。

配网屏上:OK 返回主页。它打开时设备会起自己的热点(`Passport-91E1`,WPA2),并在
`http://192.168.4.1/` 提供服务页——**串口控制台能改的每一项设置,都不用插线**。连上热点通常会自动弹出
那个页面,因为**强制门户探测路径都被应答了**。

115200 波特的串口控制台是**全部**诊断面:`help` 列出命令,[串口控制台文档](serial-cli.md)解释它们
遵守的两条契约。其中**最值得知道的是 `ui audit`**:它遍历每个屏幕,报告任何字体画不出自己文本的标签。

## 4. 桥接服务

设备是一个**薄终端**。语音识别、模型调用与语音合成**都经过局域网上的一个配套进程**,也就是
`bridge_url` 指向的东西。它的契约是[桥接协议](bridge-protocol.md),而
[`tools/mock_bridge.py`](../../../tools/mock_bridge.py) 是一个实现了全部端点的替身,因此没有真桥接也能
把设备跑起来:

```bash
python tools/mock_bridge.py --port 8080 --scenario running
# 然后在设备上:
#   config set bridge_url http://<这台主机>:8080
#   config save
```

`tools/check_device_qr.py` 把设备打印的入网二维码与一个独立实现逐格比对——**这就是没有相机也能验证符号的
办法**。

**桥接服务要变成真的还缺什么**:`/voice/transcript` 与 `/speak` 背后的服务商调用,以及 `/work-status`
背后的桌面会话。**设备侧全部写好并对着替身验证过**;真实部署是在一台电脑上实现三个 HTTP 端点,
**不需要改固件**。

## 5. 已验证,以及证据

| 领域 | 验证了什么 | 怎么验的 |
| --- | --- | --- |
| 主页 | 自己的设计:宠物、气泡、电量、提示行,以及九种可区分的表情 | `ui names`、`ui get`,并在设备上逐个走过每种表情 |
| 中文文本 | 每个标签都用**含有其字形**的字体绘制 | `ui audit`——为这件事而写,而且**它在修复前失败过** |
| 语音回合 | 按住 → 流式音频 → 转写 → DeepSeek → 朗读 → 回合归位 | 桥接服务侧逐字节核对(231,040 字节 = 7.2 秒)、转写返回、1,023 字节回答用时 2,796 ms;播放期间 `audio status` 显示麦克风关闭 |
| 音频通路 | **扬声器播放时麦克风绝不打开** | 仲裁器、它的宿主测试,以及设备在句中报出 `owner=playback, microphone=closed` |
| 朗读 | 合成音频边到边播,**整段语句持有通路** | 1 秒音频播放 16,000 个采样;之后通路释放 |
| 工作模式 | 状态文档上屏、按键选择、回答回传 | 对着局域网上真实的 HTTP 服务器,以**服务器自己的日志**为证 |
| 提示音 | 有问题或完成时响一声,其余时间安静 | 任务 running 的十秒内**全静**,状态变化时才响 |
| 配网 | 热点、强制门户、二维码、Web 后台 | 页面渲染并保存了一次提交;二维码**与参考实现逐格一致**,绘制像素**与编码器一致** |
| Web 后台 | 手机可改每一项设置,密钥从不渲染 | 由 schema 生成 19 个输入框;页面里**既无 Wi-Fi 密码也无 API Key** |
| 配置 | 19 个字段、NVS 存储、密钥打码 | 宿主测试 + 控制台 |
| 待机 | 静置熄屏、按键唤醒且不触发动作、深睡并**有序关机** | 计时的熄屏、一次只点亮屏幕的注入按键,以及一次**面板与编解码器都能生还**的睡眠 |
| 校验 | 17 个 C 测试、6 个 Python 契约测试、干净构建、校验过的合并镜像 | 逐步执行 `tools/validate.sh`;合并镜像对着分区表核对 |

## 6. 未验证

其中三项需要**人**,一项需要**设备**。

**手机能不能读出玻璃上的二维码。** 符号已经验证两次——与独立实现逐格一致,绘制像素与设备自己的编码器
一致——所以剩下的是**光学问题**:对比度、240 像素宽面板上的尺寸,以及相机。

**按键唤醒深睡。** 唤醒源已配置,并且已观察到设备入睡、被定时器唤醒。**按一下键需要一只手,而这次
工作没有那只手。**

**提示音听起来对不对。** 它们是**被测过的**——波形对着 C 库的正弦、音高靠数过零点——但**这次工作里
没有人听过它们**。

**待机电流。** 需要外接 USB 功率计,测量计划从一开始就是这么写的。**这里不编造任何数字。**

**静音阈值对真人说话是否合适。** 设备在启动时**测量自己的房间**并据此设阈值为房间峰值的两倍。房间测过了,
**对着这个麦克风说话的人没有**——所以那个余量是**有文档说明的启发式**,而不是调优值。

**真实服务商。** 所有与服务商有关的形状都是对着替身桥接服务验证的。**设备从未与商用的转写或合成服务
说过话**,而"用哪一家"这个被推迟的问题仍然开放。

## 7. 诚实的欠账

- **内存是硬约束。** 静置时最大连续空闲块约 **34 KB**,而一次 TLS 会话要吃掉其中大部分。加功能意味着
  先给它找到内存;这份文档之所以存在,部分原因就是**这条教训一路代价是一次重启循环和一次 TLS 回归**。
- **半双工在这块板子上是永久的。** 没有回声消除,所以**扬声器工作时麦克风一定是关的。打断一个回答意味着
  先取消它**,不能要求设备同时听和说。
- **掩码裁判的空缺。** 八种掩码里编码器**应该**选哪一个,从来没有对过裁判:`segno` 在填充字节上与规范不一致。
  已验证的是:**绘制出的符号在设备声称的掩码下是合法的。**
- **OTA 没有实现**,按负责人的决定推迟。
- **工作模式背后还没有真实桌面会话**喂它;协议已写好,设备侧已通过验证。
