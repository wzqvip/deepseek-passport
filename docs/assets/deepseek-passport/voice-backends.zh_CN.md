# 语音后端选项与决策

本文档回答一个问题：在这块板卡上构建实时语音对话最合适的方式是什么，以及考虑了哪些提供商选项。它记录调研、决策和被否决的选项。流水线本身在
[architecture.md](architecture.md#3-voice-conversation-pipeline) 中规定。

调研日期：2026-10-13。**提供商名称、价格和端点形态变化频繁，实施前必须重新核对。** 下文每一处价格都仅为指示性价格。

## 1. 决定设计的两个硬件事实

| 事实 | 数值 | 后果 |
| --- | --- | --- |
| Wi-Fi station 加一条 TLS 连接时的可用堆 | 约 210 KB，来自本芯片默认配置下的公开数据；文档记载的降低 RAM 占用设置可将其提升至接近 300 KB | 每增加一条并发安全连接就要花费数十 KB。流水线必须在每个阶段复用一条连接，或者更好：每个会话复用一条连接 |
| 带回声消除（AEC）的音频前端 | 不可用：本芯片不在受支持目标列表中，且每种回声消除模式还额外需要 64–126 KB 的 PSRAM | 全双工打断（插话）不可能实现。播放期间静音麦克风的半双工按键说话是唯一诚实的设计 |

第三个事实决定了传输方式的选择：与本芯片上不可用的完整音频前端不同，唤醒词模型**是**受支持的，因此免手动激活是未来的一个选项，而不是不可能的事。

## 2. 决策

**通过中继进行级联，端到端 PCM，设备上不做音频编解码器。**

```text
device: mic -> 16 kHz mono PCM16 -> one connection to the bridge
bridge: speech-to-text -> DeepSeek streaming -> text-to-speech -> PCM16
device: PCM16 -> ring buffer -> I2S -> speaker        (microphone muted)
```

### 现在该用哪些服务

中继已经写好（[`tools/passport_bridge.py`](../../../tools/passport_bridge.py)），provider 由命令行参数决定，
所以这是**选一个密钥**的问题，而不是**发一次固件**的问题：

| 环节 | 首选 | 为什么 | 在哪里 |
| --- | --- | --- | --- |
| 语音识别 | **硅基流动** `FunAudioLLM/SenseVoiceSmall` | OpenAI 兼容的 `/v1/audio/transcriptions`，中文好，一个密钥，国内可直连 | [文档](https://docs.siliconflow.cn/docs/api/audio-transcriptions-post) |
| 语音合成 | **硅基流动** `FunAudioLLM/CosyVoice2-0.5B` | **同一个密钥、同一种 OpenAI 兼容形态**（`/v1/audio/speech`，`response_format: pcm`），所以**任何地方都不需要解码器** | [模型](https://siliconflow.cn/models?q=CosyVoice2-0.5B) |
| 对话模型 | **DeepSeek** | 设备上已经在用并已验证，无需改动 | [平台](https://platform.deepseek.com/) |

**两个方向用同一个服务，关键就在这里**：设备只知道一个 `bridge_url`，而一个密钥就覆盖了需要密钥的
两个方向——这是"今晚就能用的设备"与"配了一半的设备"之间的差别。

当**中文质量比省事更重要**时，次选是**阿里云百炼**——
[qwen3-asr-flash](https://help.aliyun.com/zh/model-studio/qwen3-asr-flash) 在 OpenAI 兼容路径上做识别，
而 [qwen-tts](https://www.alibabacloud.com/help/zh/model-studio/qwen-tts-api) 走它自己的原生路径做合成；
中继的 `--provider dashscope` 模式正是为这种不对称写的。**火山豆包**的中文音色口碑最好，但它需要
多字段鉴权，所以不是默认项。

价格与模型标识变动频繁。中继里的默认值只是起点；**付费之前请点开服务商自己的页面核对**。本文档刻意
**不引用**那些它无法保持准确的按字符价格。

理由：

1. 它消除了最大的 RAM 风险（Opus 编解码器）和第二大风险（MP3 解码器加重采样）。链路两端都是原始 PCM。
2. 切换提供商变成一次配置变更，而不是一次固件发布。这*就是*需求 `R-B4`，一次解决。经由中继路由也确实让凭据不会留在可能丢失的设备上，但产品负责人已在 `Q-4` 上接受了设备端明文存储，因此这只是一项偏好，而不是规则。
3. 中继上的句子级语音合成（TTS）流水线是影响首段音频时间的最大杠杆，而且在那里实现要容易得多。
4. 良好的云端话轮检测可以取代在单个 160 MHz 核心上对它进行近似。

设备发送约 32 KB/s，接收约 32–48 KB/s，具体取决于提供商的速率。32 KB 的播放环形缓冲大约相当于 0.7–1 s 的余量。

两种部署模式下级联是相同的。它们之间改变的只是**三个阶段在哪里运行**：桥接模式下在电脑上运行，直连模式下在设备本身上运行，后者已由产品负责人在 `Q-4` 上批准。设备侧音频规则完全不变，而这正是直连模式成本可负担的原因：PCM 进、PCM 出意味着无论各阶段在哪里运行，设备都不需要编解码器、不需要重采样器，也不需要大的暂存缓冲。

## 3. 语音转文字（STT）选项

| 选项 | 传输方式 | 中间结果 | 说明 |
| --- | --- | --- | --- |
| Whisper 风格的 HTTP 转写，多个主机 | HTTP multipart，整段一次说话 | 否 | 在单一主机上每分钟后成本优势巨大，而且是最简单的客户端。没有中间转写，因此设备显示电平指示而不是实时文本 |
| 以原始 PCM 作为输入的云端流式转写 | WebSocket，`linear16` 加显式采样率 | 是 | 对设备最友好的流式选项：无容器、无编解码器、有临时结果 |
| Gemini Live | 有状态 WebSocket，原始 PCM 16 kHz 输入、24 kHz 输出 | 是 | 还做原生话轮检测，并且是唯一的单连接 PCM 输入/PCM 输出选项。但它是端到端语音模型，因此在该配置下 DeepSeek 无法充当大脑 |
| 中文流式识别服务 | 带临时结果的 WebSocket | 是 | 在中国大陆境内具有最佳中文准确度和最低延迟；各厂商端点形态不同 |
| 高吞吐主机上的批量转写 | HTTP multipart | 否 | 非常便宜、周转非常快，但没有流式 |

选择在产品负责人要求屏幕上显示中间转写结果（`Q-5`）后发生了变化：带中间结果的流式服务现在是基线，而批量 HTTP 转写是省成本的替代方案，只是不显示实时文本。中文优先的部署应优先选择国内流式服务，它同时也是普通话准确度最强的选项。

## 4. 语言模型

DeepSeek 是默认选择：OpenAI 兼容的 chat completions、Bearer 认证、以哨兵块终止的 server-sent-event 流式传输，以及让常驻可用的口袋伙伴变得可负担的价格点。任何 OpenAI 兼容端点都可以通过基础 URL 替换，这正是让该需求在实践中而非原则上可配置的原因。

DeepSeek **完全没有任何音频能力** —— 没有转写、没有合成、没有实时会话。这是相对任何单一语音到语音模型进一步支持三阶段级联的论据。

一个必须的配置细节：对话路径必须**显式禁用推理模式**。它默认启用，而在语音循环中，它的深思是用户提问与答案第一个词之间的静默空档。

## 5. 语音合成（TTS）选项

决定性的列是原始 PCM 是否可用，以及以何种采样率可用。

| 选项 | 原始 PCM 输出 | 中文质量 | 说明 |
| --- | --- | --- | --- |
| OpenAI 语音端点 | 是：原始 24 kHz 16 位小端，无头部，通过分块传输 | 正确，但韵律听感上非母语 | 零解码器路径，也是最容易集成的 |
| ElevenLabs | 是：可选 16/22.05/24 kHz，外加双向流式套接字 | 良好 | 首字节快是厂商声称并由第三方复现的，此处未独立测量 |
| Google Cloud、Azure | 是，且支持多种采样率；Azure 拥有非常广泛的中文神经语音集 | 良好（Azure 对中文尤其如此） | Azure 固定的原始 16 kHz 单声道输出无需任何设备侧工作即可匹配本编解码器 |
| 火山引擎（豆包） | 是：24 kHz PCM，以及一个双工实时端点 | 普通话同类最佳 | 中文优先产品的最强选择 |
| 阿里 CosyVoice | 是：实时流式合成 | 优秀普通话 | 有竞争力的中文价格 |
| MiniMax、Fish Audio | 提供 PCM | 强普通话 | Fish Audio 还提供实时套接字 |
| 设备端合成 | 不适用 | — | 唯一受芯片支持的设备端引擎仅支持中文，且为了一个机械感的结果仍要花费约 2.2 MB flash 和 20 KB RAM。已否决 |

首个实现的选择：选择支持原始 PCM 输出的提供商，以保持无解码器特性。中文优先的部署应把语音合成路由到国内服务，而中继让这成为一次配置变更。

**没有提供商公布可用的首字节时间数据。** 中继上的测量工具是交付物，而不是锦上添花，因为需求
`R-B7` 依赖它。

## 6. 本硬件上的编解码器裁决

| 编解码器 | 裁决 | 在本板卡上实测或公布的成本 |
| --- | --- | --- |
| 原始 PCM16 | **已选用** | 16 kHz 单声道下 32 KB/s；无 CPU、无 flash、无 RAM 开销 |
| IMA-ADPCM 4 位 | 若带宽真的成为问题时可用 | 16 kHz 单声道下 8 KB/s，成本可忽略；仓库中已有的一条经验记录记载了一个可用的软件解码器 |
| MP3 | 作为默认被否决 | 30–40 KB flash，外加在一条真实流水线中实测的 24 KiB 压缩输入缓冲 |
| Opus | **已否决** | 60–80 KB flash 外加解码所需 RAM；编码侧还希望有一个大的每线程工作缓冲，并明确说明强烈建议使用 PSRAM。在 210 KB 堆、单核且无浮点单元的情况下，这是现有选项中风险最高的 |

原始 PCM 是 32 KB/s 的局域网流量，在 Wi-Fi 上微不足道，而这正是设备完全不需要编解码器的全部原因。

## 7. 被否决的设计及原因

| 设计 | 被否决原因 |
| --- | --- |
| 像一些类似项目那样在设备上做 Opus 编码和解码 | 它们的内存策略把重分配移入 PSRAM，而本板卡没有 PSRAM，且它们当前的固件要求比本项目锁定工具链更新的 ESP-IDF 主版本。它们的协议值得研究，代码不能直接替换 |
| 通过一条实时套接字的全双工语音到语音 | 需要本硬件无法运行的回声消除，而且它会取代 DeepSeek 作为大脑 |
| 整体移植现有语音助手固件 | 工具链不匹配加上 PSRAM 假设；它还带来本项目不得复用的 UI |
| 因为“音频必须压缩”而使用压缩音频 | 这是来自带宽受限链路的条件反射。在局域网上，就本板卡短缺的每一项资源而言，PCM 都更便宜 |

## 8. 成本合理性检查

在每分钟大约十次对话轮次的情况下，使用廉价批量转写、DeepSeek 和一个中等价位合成服务的级联，每分钟成本远低于几美分。在高端提供商处的一次实时语音到语音会话，成本超过整个级联。成本在这里不是决定性因素，但它确实意味着廉价路径同时也是低风险路径。

## 9. 承诺前必须测量什么

| 测量项 | 原因 |
| --- | --- |
| 每个候选合成提供商的首段音频时间 | 没有提供商公布它，而延迟需求依赖它 |
| 禁用推理模式下大模型的首字节时间 | 确认静默空档修复有效 |
| 完整一次说话期间的峰值和最低可用堆，以及最大连续空闲块 | 本板卡的真正约束 |
| 实际扬声器在实际音量下的音频质量 | 扬声器和外壳的决定作用大于编解码器 |
